# 任务执行状态与恢复契约

日期：2026-09-11。基线：`1d77b75`。状态：待实施方案。

本方案针对定版 PRD 自动整理任务中的重复修复、人工续跑、状态覆盖、假澄清与验收失真。新增文件是因为旧的 `platform-issue-closure-loop.md` 是实施前快照，已经描述了正确意图，但没有把问题身份、版本、工作项和提交之间的关系定义成可执行约束；不回写旧方案冒充原设计已涵盖并实现。

## 1. 目标与保证边界

用户选择资料后，平台在固定输入和配置下自动整理。已完成工作不会因另一个调用失败而复活，执行中断只恢复未提交工作，真正缺业务决定时才请求用户回答。固定预算内无法完成的语义判断明确保留为平台未验证，不隐藏、不改名放行。

程序可以保证持久状态一致、有效候选至多提交一次、依赖失效必复核、失败责任明确、重复调用受限和交付使用同一已验证快照。不能保证任意自然语言 PRD 都无遗漏，也不能保证任意模型在有限调用内必然收敛。后者需要冻结样本和独立语义验收，不能通过增加重试上限宣称根治。

本轮只交付方案并纠正验收状态，不改业务代码、不操作任务数据、不发起模型重跑。

## 2. 当前证据与真正缺口

真实调试任务 `T-9695DD2E`：attempt=9，221 次模型调用，历时约 72.3 分钟（含中断调试），17 个修复候选、16 个 committed。它跨多次改代码和人工续跑，不是固定版本的独立验收。

## 3. 路线选择

| 路线 | 判断 |
| --- | --- |
| 继续增加提示词、重试、文案修正和正则去重 | 无法阻止已提交问题重开、旧结论复用和重复计费，不采用 |
| 替换为通用工作流引擎或引入事件溯源平台 | 不能自动解决业务问题身份和语义判定；当前单机单任务写者可用原子快照，不采用 |
| 收紧现有业务状态模型，统一工作项提交与恢复 | 采用；复用解析器、证据索引、Runtime、patch 校验器和原子文件写入 |

八个阶段继续用于页面说明。真正调度对象改为持久化的具体工作项，不能再依靠八个 step 的 completed/failed 决定恢复位置。业务内核集中于当前项目，不扩建通用基础设施。

## 4. 唯一状态来源与稳定身份

任务的单一原子快照包含当前业务结果、问题登记、工作项、验证记录和提交记录。页面、进度、project.audit、导出只读取该快照的投影，不允许各自修改一份问题状态。

区分四类身份：

- 输入版本：冻结文件、解析版本、来源目录及原文证据。
- 结果版本：当前功能、需求、关系和澄清的一次已提交修订，不混用输入 revision。
- 问题身份：程序首次登记时分配并永久保留，正文措辞和数组位置不参与身份定义；合并保留别名和历史关联。
- 工作项身份：具体的“确认某问题”“修复某范围”“复核某候选”，绑定目标问题、读集、候选和策略版本。

模型输出是观察或候选操作，不直接生成正式问题 ID、标记已修复或修改账本。结构问题按程序检查规则、实体和字段确定身份。语义观察由同一登记流程判断：指向已有问题、合并已有问题、发现新的独立问题或证据不足；不能用 detail 的完整文本相等或模糊相似度直接决定。

同一来源可承载多个独立决定，多个来源也可承载一个决定。因此来源集合只能辅助定位，不能单独充当语义去重键。语义归并仍需模型判断和独立反例验证；无法判断时保留为内部待核实，不自动删掉。

问题状态至少区分：待确认、已确认待修、已修复、有依据排除、待补证、关联业务决定。尝试和预算属于工作项记录，不充当问题已完成的证明。

## 5. 工作项、复核与原子提交

每项工作遵循：待执行 → 已保存候选 → 已保存复核 → 提交成功；另有拒绝、输入失效、调用失败、证据不足状态。模型调用前先保存工作项和调用记录，结果验证后再更新状态。

每次判断保存：读取的实体与来源版本、检索范围及其成员版本、使用的规则/提示词版本、判断结论与证据。尤其“未发现承接需求”的判断必须依赖整个查询范围，而不只是已读取实体；否则新增需求不会使旧的遗漏结论失效。

复核保持三类结果：原目标是否解决；候选相对基线是否引入回归；基线已经存在的旁支问题。旁支问题不否决有效修改，回归和未解决目标会拒绝候选。证据不足是独立结果，不能强迫模型二选一为通过或不成立。

提交由一个业务入口执行：

1. 检查工作项尚未提交，读集和检索范围仍有效。
2. 在当前快照副本上应用已验证候选，分配正式编号，并映射 LOCAL 引用。
3. 在同一副本登记本次观察、更新问题状态、澄清别名和受影响检查清单。
4. 校验需求图、关系、澄清引用以及全部状态迁移。
5. 将业务结果、问题状态、提交记录和结果版本一次原子写入；成功后才替换内存状态及通知页面。

若步骤 3/4 失败，不能留下“候选没提交但旁支澄清已经入库”的半成品。写盘失败不能发布已提交状态。单任务只允许一个写者；独立读取和模型调用可并行。

对候选做程序层的规范化差异检查。字段、来源、关系、归属均无变化时，不计为有效修复：若复核证明原结果已满足，则以“有依据排除/已满足”关闭旧观察；若仍存在缺口，则记无进展并停止重复相同候选。只有证据变化的有效补绑定仍可提交，不以文本未变误判为空操作。

## 6. 恢复、失效与有界调度

恢复首先读取持久化工作项，而不是重建问题列表：

| 恢复点 | 必须执行的动作 |
| --- | --- |
| 候选未持久化 | 重试该调用，计入同一预算 |
| 候选已保存，复核未完成 | 复用候选，只重试复核 |
| 复核已保存，提交未完成 | 检查依赖仍有效后提交，不重新生成 |
| 提交已完成，但页面通知丢失 | 读取提交结果并更新页面，不重复提交 |
| 相关业务内容或检查策略改变 | 将相关判断标为失效，重新核实，保留历史结果 |
| 仅无关功能改变 | 不使本工作项失效，不重发模型调用 |

恢复与重新分析是两种操作。恢复不清空问题和确认结果；用户更换 PRD 或策略升级时创建独立分析版本。现有 pipeline 9 调试记录保留为只读证据，不增加就地迁移和修 JSON 的兼容路径。

新提交只使依赖其变化的检查失效。变化域要包括实体内容、功能成员集合、关系及全局澄清目录。旧观察再次出现时先核对依赖与已关闭依据；只有新证据证明问题复发才能重新打开，不能仅因重新输出相同文字而复活。

所有责任节点进入同一工作队列：功能归属/来源分类、需求内容/引用、需求关系、澄清整理和内部归责。没有对应消费者、来源跨多个功能无法定位时，生成内部定位工作项，不得 continue 丢掉，也不要求用户替平台整理。

工作队列循环至必要检查均有效且没有可执行项。保留有界调用：单次结构纠正最多两次、同一稳定问题最多三次实质修复作为初始策略；计数持久化，重启和恢复不重置。同一读集、候选和拒绝反馈再次出现时，不重复发送相同请求。时间、调用和 token 预算也固定在分析版本中，耗尽时明确未完成，不能默认为成功。

外部模型已执行但响应未保存的网络故障，可能需要重新调用；本方案保证有效结果至多提交一次，不承诺网络调用绝不重复，也不伪造服务端已执行结果。

## 7. 业务澄清的统一准入

所有节点只能提出澄清候选，统一处理后才进入用户列表。处理时读取相关章节、流程、验收条目、原型角色和全部已有相关决定；不能因为当前分片没有答案而直接要求用户回答。

固定判断顺序：

1. 原文是否已给出答案，其他关联需求是否已经承接？有答案则补关联或改正误读。
2. 当前差异是业务行为不同，还是按钮标签、简称、示例与详细说明表达层次不同？必须说明造成哪一种可观察行为差异。
3. 存在真实矛盾时，是否有原文约定或已经配置的来源优先级？有则按该规则处理并保留依据。
4. 没有裁决依据且不同答案改变行为时，才形成业务决定；已有同一决定则关联，禁止再次新增。
5. 无法读全必要上下文或无法证明冲突成立时，保持内部未验证，不能自动升级为业务阻塞。

真实例子：正文 S-0078、流程及 AC-09 都明确确认合并后进入独立弹窗、不直接生成版本；S-0120 原型按钮写“确认合并生成版本”。这至少需要一次完整上下文判定，不能仅由短标签推断第二个完整业务规则。Q-0006/Q-0007 必须归为同一候选决定。若产品要求原型标签与正文同等约束且确实冲突，则只保留一项；不能自行制定“正文永远优先”的规则。

空字符串/纯空格的案例则明确写着需要统计实际数据并由技术评审决定。没有实际统计和评审结论时，平台应保留这个实施前置决定，而不是猜一个默认答案。

合并由显式操作给出合并对象、唯一未决点、合并依据和合并后内容；禁止依靠 duplicate/重复关键词直接删除条目。合并保留来源、不同条件、已答事实、历史关联，重算所有 Q 引用和相关工作项；保留别名而非静默忽略不存在的 Q。两个不同决定共享原文必须保持独立。

等级按合并后唯一决定重新评估，不能永久取历史最高等级掩盖误判：阻塞表示必须由业务选择且改变实现；建议必须有原文允许的明确默认口径；可忽略只涉及不会影响实现的表述问题。降级也必须保存依据，不能用降级消除阻塞。

最后任何节点新增或修改澄清，都使全局澄清一致性检查失效；不能刚合并完又由末次审计产生 Q-0007，却仍沿用先前通过结果。

## 8. 输出契约、最终准入与用户状态

将现有提示 schema 和接收校验整理为共用的结构契约，明确可选字段缺失、null、空字符串的含义。类型错误在产生响应的工作项边界处理，不冒充另一阶段失败。程序生成原文证据和内部元数据，模型只选择证据、提出观察与内容改动。结构契约测试可脱离模型执行；结构合格不代替语义判断。

预先建立必要检查清单：来源处理与处置、功能归属、内容忠实性与完整性、关系、澄清一致性。最终对同一个结果版本要求：

- 必要检查无缺项、无运行中、无证据不足，所有读集仍有效。
- 平台问题都有合法处置记录，不能仅检查 open 数量。
- 功能/需求/关系/澄清无非法引用、未处置来源或程序发现的重复实体。
- 独立语义检查完成，业务决定没有被当成确定需求；同一决定未重复列出。
- 生成包使用该结果版本，包清单与最终准入记录匹配。

准入检查自己发现问题时也要进入队列；在预算内继续修，预算外明确未完成。模型给出的 UNKNOWN、超时和没有审计结果均不能视为无问题。

状态只从这一份准入结论派生：正在整理；平台未完成；需要业务确认；可交付。需业务确认时必须显示唯一业务决定及其完整依据；不把推断不成立的冲突发给用户。澄清答案提交与后续新输入版本复用已有后续轮次设计，不在此次执行内核重构中另起一套。

## 9. 实施顺序与需要移除的旧路径

1. 冻结 T-9695DD2E 的调试证据，撤回 round 5 根治通过结论；先写当前反例测试并确保能够失败。
2. 在 `src/types.ts` 定义输入/结果版本、稳定问题、工作项和检查证明；在现有调度器收敛一个提交/恢复入口。若当前单文件放不下，将业务状态迁移提取为一个可纯函数测试的模块，不建立通用工作流库。
3. 改造 `audit-repair.ts` 的规划与增量预应用，接入读集检查、无进展判定和原子提交。
4. 所有审计观察、关系、功能返工和澄清统一进入登记与调度；删掉重建问题数组、按 step 重跑、裸 ID 确认集合、字符串匹配合并及直接修改项目的旧路径。
5. 接入版本化最终检查，页面、导出、恢复使用同一判定；协议升级后用原始材料新建验收任务。
6. 按下表验收后再更新能力说明；源码测试、运行稳定性、业务语义三项分别给结果。

## 10. 验收标准

| 场景 | 必须看到的结果 |
| --- | --- |
| A-0011 已修复，后续 A-0017 确认失败再重启 | A-0011 不重新生成候选、不再计一次修复；仅恢复 A-0017 |
| 在候选保存前后、复核保存前后、原子提交前后分别中断 | 对每个断点恢复后业务图和问题状态一致，每个候选至多一次有效提交 |
| 新审计分片顺序变化、插入一项问题 | 原问题 ID、处置证据、预算保持；不按新数组位置关联旧记录 |
| 旧遗漏问题重新输出，但需求早已补齐 | 校验当前事实后排除旧观察，不能因缓存把问题重新打开 |
| 原问题解决但发现旁支；或候选引入回归 | 前者原目标提交且旁支独立调度，后者拒绝且不污染业务图 |
| 候选内容和全部证据均无变化 | 不计有效提交；已满足则更正审计结论，否则记无进展 |
| 相关需求变化/无关需求变化/查询范围新增需求 | 分别失效重验/继续复用/失效遗漏判断 |
| Q-0006/Q-0007 同义，或两种独立决定共享来源 | 前者唯一登记，后者不合并；重复操作不新增实体且引用完整 |
| 澄清合并后崩溃或后续审计又提出同一决定 | 同一快照内恢复，旧引用可追溯，最终一致性检查重新执行 |
| 原文已明确行为，仅标签不一致；真实原文未决 | 前者不因单个标签虚构阻塞，后者保留一次且写明缺失的决定 |
| 任一必要检查为 UNKNOWN/过期/缺失 | 保持平台未完成，不能仅凭问题数为零放行 |
| 三次全新真实任务 | 同一冻结代码、输入、模型配置；中途不改代码、不手动续跑、不编辑任务 JSON；均正常到达可交付或唯一真实业务决定边界 |

三个新任务允许文字措辞不同，但关键业务规则和业务决定集合必须与独立冻结的预期一致。人工逐项核对点击跳转、表头筛选、导出字段及版本来源排除、确认合并后独立确认、空值决定等样本；不能用同一个生成模型自评或关键词命中替代。

调用成本单独记录。不存在通用于全部 PRD 的固定“最多 N 次”承诺；首先要求同一依赖版本下的已提交工作不重复、无变化修复为零、串行范围外可并行。总预算按检查清单确定并在运行前冻结，超过即失败，不边跑边扩大预算来凑通过。

## 11. 缺少什么，是否阻碍方案实施

已具备：真实定版 PRD、失败任务记录、完整源码、模型接入和本地运行环境。无需用户再补平台使用场景，也不需要接入真实开发仓库才能修复执行一致性。

实施尚缺的工程产物：上述统一状态契约的代码、跨所有断点的失败注入测试、不能由模型随意改写的语义验收样本、固定版本全新任务的成功证据。这些应由开发侧补齐，不能转嫁给用户回答。

只有具体业务结论可能缺外部事实：空值实际数据统计与技术评审结论；如果完整上下文仍不足以裁定原型/正文冲突，则缺该材料的约束优先级。它们只阻止相关业务决定被自动回答，不阻止平台执行内核重构。未建立这些依据前，不承诺这份 PRD 必然零业务阻塞。
