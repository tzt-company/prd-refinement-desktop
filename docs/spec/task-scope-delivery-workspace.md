# 任务管理、本期范围与交付工作台

日期：2026-09-13。状态：已实施。本文件以用户本轮五项要求为准，替代旧方案中“阻塞事项必须清零才能交付”和临时功能勾选即交付范围的约定。

## 目标与现状

用户拿到定版 PRD 后，需要审阅已有结果、一次描述调整意见、决定哪些内容本期做，再把当前范围和未决事项一起交付给开发 Agent。任务归档、事项处理、范围选择、产物生成是不同动作，不能互相替代。

本轮只读核对确认：

- `src/App.tsx:43` 将执行状态、业务事项及能否交付混在任务页；各信息块没有统一布局所有者。`src/styles.css:1` 的页面最大宽度为 1320px，进度卡为 760px，提示卡为 650px，错误和执行状态下明显宽窄不齐。
- `electron/export-agent-package.ts:64` 起的 deliveryScope 会因阻塞澄清、reviewed 状态等排除整个功能，再沿关系双向扩大排除；用户选择的内容未必进入实际交付包。
- `electron/main.ts:151` 打开目录时根据任务 ID 拼路径并 mkdir；没有查询已经发布的产物。标题按钮没有捕获异常；功能页将导出和打开目录包在同一异常处理里，无法区分失败阶段。
- 日志 `docs/tmp/npm-start-20260912-233130.out.log:22` 和 26 为 analysis:export-package 的“当前任务还没有可导出的结果”。当前读取的 T-DD1D9FB1、T-C5E8F68D、T-9695DD2E、T-91746676 均无 resultVersion，但存在结果目录；页面以默认第 1 版展示，主进程却拒绝缺少 resultVersion 的导出请求。
- 尚未捕获用户那一次 shell.openPath 的返回错误，不能把导出版本错误断言为打开目录失败的唯一根因。
- 任务尚无归档/删除接口；功能勾选只是页面临时状态，需求没有批量范围操作。

## 一、任务管理

以用户看到的一个任务（含全部结果版本和调整记录）作为归档和删除单位。任务列表增加“当前任务 / 已归档”，行末操作菜单与详情页“更多”复用同一动作。

- 归档：移入已归档列表，保留原材料快照、结果、版本和调整记录；可恢复。默认列表及统计排除已归档任务。
- 删除：一次应用内确认，显示任务名称、版本数量及将删除的托管记录、检查点、输入快照和产物。删除完成后回到列表并移除本地草稿。
- 有排队/执行中的任务或调整时，不直接删除/归档；先停止执行并确认后台退出、持久化写入结束，再进行用户已选择的管理动作。
- 不删除用户原始文件、独立资料包或已经复制到外部目录的交付文件。共享输入快照只有没有其他任务引用才回收。

后台在任务族上串行处理管理动作。先持久化删除标记并撤出队列，再清理资源；重启不恢复删除中的任务，迟到回调也不能重新写出已删除记录。清理失败可重试，页面准确标为“删除未完成”。归档字段独立于执行状态。

## 二、存在待处理事项仍然交付

交付以本期范围和当前保存的结果为准，不要求待处理事项为零；阻塞、建议、可忽略继续表示问题的重要性，不再作为整个包能否生成的开关。

- 有本期需求且能够成功序列化、落盘，就能生成交付包。首次任务尚未形成结果、没有任何本期需求、快照损坏或文件写入失败时，说明具体原因。
- 阻塞澄清不会让整个功能被自动剔除，也不会沿普通关系自动扩大剔除范围。
- 待澄清问题随相关需求进入交付包，保留问题、现有依据、影响范围、级别和状态。Agent 明确得知哪些规则尚未决定，不能替用户补答案；不依赖这些决定的内容可以先实施。
- 对平台核查失败或无依据内容也可导出，但其质量标记必须保留，不能改写为“已验证可实施”。未知规则不生成默认值，不因交付自动关闭问题。
- 页面任务状态使用“已完成 / 执行失败 / 执行中”等执行描述；旁边独立显示“待处理 13 项”。交付记录显示“已交付第 N 版”，不将“可交付”当成质量认证。
- 待处理页同时展示“影响本期 / 仅影响本期不做”范围；用户可筛选，本期不做不会自动消除问题。

一份交付包包含本期需求、相关待处理事项、本期不做清单、来源和版本清单。JSON、Markdown、Excel 同源，主需求集均只包含本期需求。机器入口明确区分“本期要求、未决规则、核查状态、排除范围”。生成按钮直接执行，不增加逐条确认或强制清零流程。

## 三、任务详情重新设计

比较三个布局：

| 候选 | 选择 | 理由 |
| --- | --- | --- |
| 继续堆卡片，只统一 CSS 宽度 | 排除 | 只能修边缘，不能解决成本、提示、输入框挤占首屏和重复操作入口 |
| 固定左右双栏，左侧输入、右侧结果 | 排除 | 长需求和中文表格被压窄，1100px 桌面窗口尤其难读 |
| 单一内容框架，紧凑任务栏、结果主体、统一调整区 | 采用 | 主要空间留给审阅和批量范围管理，任务动作始终清楚可达 |

页面结构：

```text
返回任务中心
任务名称 · 当前版本                    [生成交付包] [打开产物] [更多]
已完成 · 本期 76 条 · 本期不做 12 条 · 待处理 13 项 · 耗时/用量 ▾
──────────────────────────────────────────────────────────────
功能与需求  |  全部需求  |  待处理事项 13  |  执行记录
搜索…  [本期 / 本期不做 / 全部]                 范围与数量
已选 8 项        [标记本期不做] [恢复本期] [取消选择]
功能分组或需求列表                                  查看依据 →
──────────────────────────────────────────────────────────────
描述你希望怎么调整（同一个输入框，可展开）
例如：退款审核按流程展开；金额统一按含税处理……       [按说明调整]
```

- 完成任务默认打开“功能与需求”；删除重复“概览”大指标卡，统计收进一行摘要。执行中默认打开执行记录；形成的上一个正式结果仍可阅读。
- 外层统一最大宽度 1320px、水平内边距 24px，各整行区域 width:100%、min-width:0。进度、失败反馈、列表、输入区全部服从同一个容器，删除各自独立的 650/760px 居中规则。
- 标题、工具栏、表格和输入区内容左边缘一致。正文采用现有微软雅黑 UI；标题 20px、正文 14px、辅助信息 12px，正文行高 1.6；沿用蓝色操作、青色来源和红/琥珀/灰事项等级，不引入新主题。
- 统一输入区在结果主体下方，默认约三行，可展开；长页面滚动时保留紧凑输入操作区，展开后占据正常空间，不覆盖表格、焦点和底部行。草稿不因切换标签/筛选丢失。
- 成本、Token 和模型明细放入“耗时/用量”展开区和执行记录，不再固定占用结果页首屏。
- 错误采用同宽、左对齐的就地反馈，不再跳出窄卡。输入提交、产物生成、打开目录分别呈现进行中/成功/失败。
- 详情抽屉只用于阅读依据和需求详情。调整仍用一个自然语言输入框；本期范围用明确批量操作。
- 1100px、1440px、1920px 均对齐；窄窗口工具栏换行，表格必要时局部横滚，长中文和错误不会扩大整页宽度。

## 四、产物目录打开修复

将“生成交付包”和“打开产物”拆成独立接口和独立 UI 状态。生成成功但系统目录打开失败时显示“交付包已生成，目录未能打开”，提供重试与复制实际路径，不提示重新生成。

后台以任务及当前查看版本查找真实已发布产物，生成时保存并回读目录记录；打开请求不创建空目录。不存在产物时显示“尚未生成产物”，可执行生成；目录已被外部删除时如实提示重新生成。路径由主进程从任务记录解析并校验，渲染进程不传任意目录。

“打开产物”默认打开当前查看版本最近一次交付包的确切目录；已有历史草稿时列出并标识，避免用户打开 result 父目录后仍需猜测哪个子目录是最新产物。

旧任务版本问题在读取层做一次规范化：按真实保存结果和父子关系确定版本，持久化后前后端共用。无可确认结果的记录保持“未形成结果”；不能所有旧任务都强行赋 1，也不能只放宽接口检查。已有产物的打开不依赖新增版本字段齐全。

验证实际故障时分别读取 IPC 参数、记录路径、文件存在性、权限和 shell.openPath 错误；记录技术日志，页面提供可理解的原因。必须在本机 Electron 中确认资源管理器打开正确目录，浏览器演示态和进程存活不能替代该验证。

## 五、批量标记本期不做

新增持久化范围状态“本期 / 本期不做”，独立于核查状态、澄清状态和执行状态。默认已有需求均为本期；历史快照及已导出的交付包保持原样。

- 功能列表和需求列表均支持行复选框、表头全选本页、选择当前筛选全部结果；明确显示选择数量及跨页范围。切换筛选清空选择并反馈，防止隐藏选择造成误操作。
- 选中后显示统一批量操作条：“标记本期不做 / 恢复本期 / 取消选择”。一步提交，不要求填写理由，不弹出逐项表单；结果可撤销。
- 选择整个功能即将其需求全部排除；只选部分需求则功能显示“部分纳入（6/10）”。恢复功能使其全部需求恢复本期，按钮提示影响数量。功能整项排除记录保留，可约束后续该功能新增需求。
- 不物理删除需求，不改变原文，不把澄清标记已解决。范围变化通过程序执行，不调用模型，不重新细化。
- 保存为新的结果版本，包含操作者、目标、变更前后和时间；沿用任务族版本冲突检查。用户在旧版本操作时引导切换最新版并保留选择，不能覆盖新结果。
- 需求调整保留稳定身份和范围决定。拆分继承原需求范围；合并不同范围的需求须保留可区分的范围，不能静默把排除内容带回本期。整功能排除时新增需求继续排除，范围无法可靠继承时保留旧版并指出冲突。
- 本期需求依赖本期不做内容时，展示相关对象和影响，随包记录外部/未满足依赖；不自动恢复或扩大排除范围，不把依赖边静默丢掉。

现有临时“选择交付功能”改为上述持久化范围管理；顶部“生成交付包”始终读取保存后的本期范围。复选框表达的是本次批量编辑选择，范围标签表达的是已保存决定，两者不可混用。

## 实施与验收顺序

1. 定义任务生命周期、结果版本、本期范围与交付包契约，先修旧任务版本规范化和产物查询/打开。
2. 实现范围的无模型批量更新、持久化、继承和版本冲突保护；修改交付编译器，使问题随包保留且不再自动剔除整个功能。
3. 统一任务详情布局和范围工具栏，加入归档/删除，同步 README、DESIGN、UX 契约。
4. 使用固定数据验证事务和导出；使用真实 Electron 验证目录打开、归档恢复、删除及页面操作，再报告完成。

关键验收：有阻塞/建议/可忽略共 13 项仍可生成非空本期交付包，所有问题保留；批量排除两个功能和三条需求后重启仍生效，恢复及重新生成不误改范围；未满足依赖在包内可见；归档含完整版本且可恢复，运行/删除竞态不会复活任务，共享资料不被误删；旧任务已有产物可打开；生成成功与打开失败能独立表达；各状态页面区域左右边界一致，统一输入区和批量操作可通过键盘使用。

实现已覆盖任务族归档、恢复和删除，持久化本期范围、交付包编译、真实产物记录与打开，以及统一任务详情工作台。验收记录与截图见 `docs/acceptance/source-reference-integrity/round-20.md`；系统目录调用仍以本机 Electron 的实际返回值为准。
