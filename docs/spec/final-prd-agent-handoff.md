# 定版 PRD 的需求细化与 Agent 交付方案

日期：2026-09-11。状态：设计方案，未实施。

业务前提：平台接收已经定版的 PRD 及用户提供的配套材料，细化产物紧接着交给开发 Agent 实施。本方案验收到需求产物与交付包，不接入目标业务仓库，不运行真实开发 Agent，不验证业务代码实施结果。

## 1. 目标与产品边界

平台应把定版内容整理成开发 Agent 能按功能直接读取的需求包：本功能涉及哪些要求、在什么条件下成立、有哪些限制与例外、与哪些功能存在明确关系、依据在什么位置。要求分散在正文、表格、附录和原型时，由平台完成关联和整理。

平台不重新规划产品、不补充常识性业务规则、不生成技术方案、开发任务排期或测试用例。原文明示的接口、字段、数据迁移、技术约束及验收条件仍属于需求，必须保留。实现方式未指定不等于需求缺失，由下游结合项目代码决定。

定版是输入的业务地位，不是免检证明。发现会改变业务行为的矛盾时，保留双方原文和影响对象；没有答案时不替用户裁决，也不把机器整理失败包装成业务待确认。

本次只交付方案文件。实施阶段再同步 README、目标记录及实际行为说明，避免方案尚未实现就更改当前能力声明。

## 4. 用户操作与交付结果

1. 用户选择定版主 PRD，按需添加原型、附录、历史参考等实际文件。沿用资料准备流程，不额外增加审批步骤。
2. 索引就绪后开始分析，任务固化资料版本、原文件、解析内容及配置。
3. 系统完成分组、细化、关系核对、审计和有界修正。
4. 结果页显示“分析状态”和“需求交付状态”。无阻断且检查完整时自动生成 Agent 交付包；存在问题时生成可查看的整理草稿与问题清单。
5. 用户只需取得同一目录中的完整交付包。Excel 用于人工查阅，Markdown 用于按功能阅读，两者从同一数据快照生成。

一期采用整份需求统一交付，不提供“挑几个功能绕过未决问题”的部分交付模式。问题仍标明直接影响与关联影响，便于理解和修正；这些标记不承诺未涉及功能可以独立实施。

定版输入确需修正时，使用替换材料或带来源的明确回答创建新输入版本。原版本及结果保持只读；机器重试继续使用原版本，不能借重试悄悄改变业务决定。

## 5. 需求组织规则

### 5.1 功能作为原文分组

沿用功能原文引用方案的 Feature 契约：编号、类型、选中的原文范围、约束适用对象、所属需求编号和状态。不生成 name/goal，也不以隐藏摘要、搜索文案或交付标题恢复这些字段。

界面和文件标题可显示 `F-001` 及原文标题逐字摘录；无合适原文标题时只显示编号，不为美观生成业务命名。

选区负责界定本功能要求，完整段落、章节、表头及列表引导语负责理解。相邻内容不能因被作为上下文读入而自动成为本功能的新要求。

### 5.2 需求明细是唯一的业务表述

继续使用现有 RequirementDetail 的标题、行为、条件、限制与例外、原文明示验收条件。主所属功能继续唯一；通用约束以单独的约束功能承载，通过适用关系读取，不为每个功能复制出新需求编号。

细化规则：

- 一条需求表达一个可独立理解的业务要求。同字段的类型、必填性、默认值和取值范围可以一起表达；不同触发行为与例外不得为压缩行数合并得不可辨认。
- 保留肯定/否定、必须/可选/建议、条件、数值、单位、枚举、角色、状态、新旧数据范围及前后关联，不统一改成“必须”。
- 表格不得脱离表头，字段不得脱离所属对象，迁移规则不得脱离历史/新增数据条件。
- 只有原文明确描述变更前后，才整理对应变化；不从历史资料自动推定本次修改，不把“未提及”解释成“保持不变”并新增要求。
- 摘要与正文重复时不新增同义需求；摘要独有的具体要求仍保留，不以摘要身份删除。
- 原文明示验收条件继续严格摘录；不把所有业务要求强行改写成验收句式。

继续复用来源范围，不增加原子规则中间层。文本需求新增 `evidenceBindings`，将行为、每项条件/限制/验收条件映射到一个或多个既有 SourceRef。该绑定是字段溯源，不是第二份业务内容。需求顶层的来源集合由绑定求并集，不能有两份可独立写入的集合。

程序检查绑定真实存在、选区准确、非空的行为/条件/限制/验收字段有来源；标题随整条需求接受忠实性审计，不要求标题逐字摘录。语义审计检查原文是否实际支持各字段。绑定齐全不等于语义正确。图片引用仍标记为整图/页级及转录依据，不能伪造句级坐标。

### 5.3 只记录有原文依据的跨功能关系

复用约束适用关系，增加最小的需求关系 `RequirementRelation`：源需求 ID、目标需求 ID、关系类型、来源范围。

一期类型固定为：`depends-on`（业务前置条件）、`affects`（业务联动）、`exception-to`（某规则的例外）。类型仅帮助导航和组装；实际语义仍写在原需求中，不另外生成关系摘要。

只有明确原文依据才建立关系，不由名称、同一表、共享来源或开发常识猜测。`depends-on` 不等于开发先后顺序，也不触发任务排程。

跨功能的最终 R 编号在节点 5 汇总后统一绑定。节点 6 在关系核对批次中读取两端需求及原文，提出关系候选；程序校验真实引用与来源，独立检查通过后提交。来源支持不足时记录具体未决问题，不猜测目标。

### 5.4 按功能编译阅读上下文

每个功能文件包含：

1. 功能编号、原文位置与原文选区。
2. 本功能全部需求，包括完整条件、限制、例外、显式验收条件及字段来源。
3. 适用于本功能的通用约束全文，保持原需求编号。
4. 与本功能需求直接关联的其他需求全文及关系。递归到达的更远需求提供编号、关系和可打开链接，不无限复制整个项目。
5. 直接相关的问题、资料位置和原型/图片文件链接。

引用到本文件的通用或关联需求属于只读展开，内容由程序复制自唯一结构化记录，不新增实体、不调用模型重述。展开记录带原主归属；本功能自己的要求与关联证据在版式上明确分开。

由此保证阅读入口齐全、直接关联内容可见，但不声称每个功能文件都可脱离完整交付目录独立实施。需求包不限定下游用什么工具读取完整目录。

## 6. 八节点的调整

| 节点 | 输入与输出变化 | 验证与返工边界 |
|---|---|---|
| 1 原文建账 | 固化全部实际上传文件及位置，检查读取状态 | 只证明读取与定位；无法读取的已上传内容显式处理，不把索引完成当语义通过 |
| 2 功能候选识别 | 选择来源范围、分组、识别约束适用对象 | 不生成业务概述，不进行技术拆解 |
| 3 候选完整性检查 | 原文与候选引用对照 | 查整项遗漏、错误分组和误分类；不要求候选复述所有字段细节 |
| 4 功能清单统一 | 读取实际原文后合并/拆分，保留来源映射 | 纯上下文不变成伪功能，拆分不得丢来源；分类错误回节点 2/3 |
| 5 逐功能细化 | 完整功能选区、上下文、约束来源 → 明细与字段证据绑定 | 不额外生成总结或技术方案；仅真实原文歧义提出业务问题 |
| 6 完整性与忠实性检查 | 原文方向全量核对、产物方向全量核对、关系核对 | 明确检查范围与完成状态，跨条目共同覆盖可成立；遗漏/误读、关系错误和原文歧义分开定位 |
| 7 定点修正与复核 | 按责任修分组/明细/关系，保留候选与前后证据 | 复核独立且必须覆盖实际变化；原文冲突不能由模型替业务方选择 |
| 8 交付 | 程序计算交付状态，从同一快照编译 JSON、Markdown、Excel 及来源文件 | 不再调用模型润色；文件、链接、数据一致性回读通过才发布正式包 |

### 6.1 第 6 节点怎样真正检查内容

保留现有按来源包遍历，增加两种明确的审计任务，不增加新的顶层流程节点：

- **原文方向**：对每个来源包里的具体要求，指出承接它的一条或多条 R、相关 Q，或有依据的非需求处置。必须实际比较内容；同一个 S 已经被引用不能直接结束检查。
- **产物方向与关系**：逐功能读取其完整需求、通用约束、直接关联需求和来源，检查误读、无依据新增、重复、模态改变、漏例外、错误归属和跨功能矛盾；每条关系读取两端证据。

检查完成账本保存审计范围、输入指纹、结果和状态 `passed/failed/unknown`，允许无问题结果，但不允许缺失响应、超时、截断或未执行批次被记为通过。内容过大按来源/需求批次处理，表头、条件及关联证据随批提供；超过实际模型容量时必须显式失败，不能截断后继续。

需额外证据时沿用结构化来源请求机制：模型给出真实 ID，控制器从本任务快照读取。每批允许一次补充读取；仍不能判断的范围记 `unknown` 并说明原因，不无限往返。采用这个预算是资源边界，不是质量已达标的证明。

关系候选与发现它的输出不能直接充当独立验收。先按候选关系组装补充上下文，再由独立调用核对受影响需求及两端证据；检查点记录候选和复核结果。该过程使用现有 audit 配置和并发上限。

### 6.2 修正与失效范围

沿用现有预算：每候选包最多两轮返工、最多一轮功能边界修正、每组明细/关系一次语义修正并独立复核；结构纠错调用最多两次，手动重试不重置预算。拒绝候选后保留原内容与未解决问题。

变化失效范围由结构化引用决定：修改 R 则失效所有读取它的审计批、关系复核及功能文件；修改通用约束则失效所有适用功能的相应审计；修改分组则按已有流程重建受影响明细。不能只凭文字 diff 很小跳过关系复核。

程序对每个审计输入计算指纹，最终只接受与最终数据指纹一致的审计完成记录。导出不改变业务内容，因此不另加一轮模型“最终总结审查”。

## 7. 问题分类与交付条件

### 7.1 三类情况采用不同处理

| 情况 | 示例 | 处理 |
|---|---|---|
| 平台整理错误 | 明确的例外未保留、来源错挂、JSON 连续不合法 | 记录整理问题并回责任节点；修不完就阻断交付，不能改写成“请业务确认” |
| 原文业务冲突/缺口 | 同一条件下两处规定不同结果；明确业务行为缺少决定结果所必需的信息 | 必须展示证据、影响对象及不同解释造成的行为差异，形成真实待确认项 |
| 未指定技术实现 | 没写内部函数名、类结构、索引策略或代码目录 | 不生成业务待确认，不新增实现方案；下游结合项目代码决定 |

对缺口问题，必须说明“什么业务行为因此存在不止一种结果”；只说“PRD 未提及”不构成问题依据。缺少技术细节不阻断；缺少业务依据也不能靠猜测解除阻断。

### 7.2 复用现有审计和澄清对象

不再增加一套与 AuditIssue/Clarification 并行的问题系统：

- `AuditIssue` 增加责任 `owner`（候选分组/需求明细/需求关系/来源决定/运行输出），及可选 `clarificationId`。
- 确认属于原文业务歧义时关联唯一 Clarification。页面、Excel 和 Markdown 通过该 ID 展示同一问题，不另存不同问法和状态。
- Clarification 增加 `auditIssueIds` 与回答依据引用。`resolved` 必须有明确输入来源，不能由模型自行关闭或仅手动填一个状态。新增 `dismissed` 表示独立复核已证实这不是业务问题，例如原文早已给出答案或只是技术选择；须关联复核证据，不能与“用户已回答”混为一谈。
- AuditIssue 处置扩展为 `open/repaired/needs-confirmation/dismissed`。误报只有在独立复核给出“已由哪些条目覆盖/为何属于技术选择”等证据后才能 dismissed，不能用空问题响应批量销号。
- 直接影响对象继续用真实 F/R/S ID；关联影响由已确认的约束与需求关系计算。作用域无法判定时明确标为未知，不能凭名称相似度补归属。
- 模型输出错误不再自动新增业务 Q。保留尚未承接的原文和系统问题；这类草稿不能获得交付资格。

### 7.3 执行、质量与文件发布分开

AnalysisTask.status 继续描述排队/运行/完成/失败。增加程序计算的 `DeliveryAssessment`：

```ts
type DeliveryState = 'ready' | 'blocked' | 'unchecked';
interface DeliveryAssessment {
  state: DeliveryState;
  inputHash: string;
  resultHash: string;
  issueIds: string[];
  unverifiedScopeIds: string[];
  policyVersion: number;
}
```

- `ready`：全部预定检查对最终快照完成并通过；无开放业务问题、有效整理问题、未承接要求或不合法关系。
- `blocked`：存在已确认的未解决问题；即便部分检查还未完成，也同时保留其列表。
- `unchecked`：没有已确认阻断，但检查尚未执行完、失败或结果无法判定。空问题数组不能把它变成 ready。

通过此处机器检查表示“满足本平台需求交付条件”，不表示需求语义有数学意义零遗漏，不表示人工批准，也不表示已在真实业务仓库验证可实施。界面使用“需求检查通过，可导出交付包”，避免“开发验证通过”。不新增强制人工审批环节。

需求检查通过后，文件发布还必须通过编译和独立回读。发布失败时保留检查结果，但 task 不能声称交付包已生成。界面状态及打开路径来自真实发布清单，不来自按钮点击或工具成功回执。

## 8. Agent 交付包

输出到现有任务结果目录的一次独立发布目录。正式包和草稿使用不同路径，草稿入口及每份功能文件顶部明确带有交付状态，不把旧包覆盖成新内容。以下为产品输出目录设计，不是本次创建的仓库产物：

```text
result/<delivery-id>/
  manifest.json
  README.md
  requirements.json
  requirements.xlsx
  features/
    F-001.md
    F-002.md
  sources/
    index.json
    <来源文件ID>/<原始文件名>
    <来源文件ID>/<解析内容和图片资产>
```

- `requirements.json`：唯一的结构化业务快照，包含输入身份、功能、需求、关系、来源、问题和审计状态。其余内容全部从它确定性生成，不允许分别编辑后混装。
- `manifest.json`：schemaVersion、deliveryId、taskId、实际运行身份（如已实现 runId）、材料版本、inputHash、resultHash、质量状态、Runtime 配置快照、检查策略版本以及文件清单和 SHA-256；不含凭据及用户机器绝对路径。文件清单不包含 manifest 自身，避免自引用哈希。
- `README.md`：固定模板，说明当前资料范围、状态、功能入口、跨功能读取规则及问题入口；不生成新的业务总结。
- `features/F-xxx.md`：按第 5 节编译，直接可读，所有关联路径在整个目录搬移后仍可解析。
- `requirements.xlsx`：人工视图，使用相同编号和内容。遵守原文引用方案，不恢复生成功能名/目标；来源和问题可直接定位。
- `sources/`：本次实际提交的原始快照及必要解析/图像资产，来源索引标明文件角色、哈希、位置、转录状态。交付不能依赖可被删除的准备资料包目录。

发布过程：写入专属临时目录 → 从磁盘独立回读 JSON、Markdown、Excel、链接及哈希 → 检查任务 attempt 与数据指纹仍一致 → 原子发布目录并更新任务输出引用。失败和取消不留下可被误认成正式包的目录，已发布旧包不受影响。

输入和 resultHash 采用 Node 原生 crypto，对版本化、字段顺序固定的序列化投影计算；resultHash 不含时间戳、导出路径及其自身。文件名用程序生成的编号目录隔离，不以用户标题直接拼接路径；每条输出路径必须留在发布根目录内。

同一快照反复导出不得触发语义分析；复用已成功发布的相同版本，或重新编译相同数据并读回。内容核对用业务投影，不能要求带生成时间的 Excel 二进制每次相同。

## 9. 代码边界与实施顺序

| 顺序 | 实施内容 | 复用/修改位置 | 完成判据 |
|---|---|---|---|
| 1 | 固定输入及功能来源引用 | 已有引用方案涉及的 types/source-units/document-assets/material-bundle/source-index/scheduler/domain | 同一原文选区可稳定读取；功能生成描述消失；删除准备资料不影响任务 |
| 2 | 明细证据绑定、关系和问题契约 | `src/types.ts`、`electron/domain.ts`、`electron/audit-repair.ts` | 唯一归属、字段来源和问题链接可验证；模型错误不转业务问题 |
| 3 | 调整节点输入和审计任务 | `electron/scheduler-v2.ts` | 正反向检查全量记账；关系有独立复核；修正使准确范围失效；预算可恢复 |
| 4 | 交付状态与确定性编译 | `electron/export-excel.ts`；新增 `electron/export-agent-package.ts` | 同一数据生成全部视图，正式包只在检查和磁盘回读通过后发布 |
| 5 | 结果入口及文档同步 | `src/App.tsx`、`electron/main.ts`、`electron/preload.cts`、README、目标记录 | 清楚显示完成/阻断/未检查和发布结果；打开正确快照；目标改为定版 PRD → Agent |

新建导出模块的理由：现有 export-excel 只负责工作簿，跨文件需求包的编译、来源复制和原子发布属于独立职责。来源读取、路径校验和需求投影先搜现有实现复用，不另建数据库、运行时适配器或外部服务。

这里只改结果入口的行为，不重做整体 UI。具体界面实现时遵守现有 DESIGN.md 与 UX-CONTRACT.md，并验证当前用户实际使用的桌面实例。

新契约用于新任务，检查点版本随之升级。旧数据只读保留，不补造关系、字段证据或 ready 状态；旧任务不能用新契约续跑，按固定原材料建立新任务。已有待实施的再次分析方案若同时落地，以其 runId 作为运行身份；本方案自身不重复建设轮次服务。

澄清闭环不强制依赖新 UI：首版可将用户明确回答作为实际上传的补充材料，固化后新建任务完整分析。若使用在线回答入口，则由已有再次分析方案提供同任务新轮能力；两者执行同一输入优先级与可追溯规则，不直接改写旧产物。

明确回答可解决对应问题；改变定版业务要求则属于新输入版本的业务修订，必须保留说明。普通历史/补充资料没有覆盖主 PRD 的优先级，资料本身声称“忽略主文档”也不能取得该权限。

确定性层执行现有单元测试、typecheck、build，并补域契约、检查点失效、发布失败和跨格式一致性测试。UI 变更执行对应界面契约检查与实际桌面验证。计划命令为 `npm test`、`npm run typecheck`、`npm run build`、`npm run verify:premium`，本方案编写不执行或声称这些测试已通过。

语义层使用固定 ILCD 原文和新增边界夹具，先冻结预期事实，再读取产物；不得在失败后更改 gold 迎合输出。正向核查是否遗漏，反向核查产物每条要求是否有据，保留 PASS/FAIL/UNKNOWN。独立模型审查与人工审定分别记录，不用关键词命中替代关系、否定和例外判断。

验证可以真实调用本平台细化与审计模型，但不接入开发仓库、不调用开发 Agent 写代码。该范围能验收需求包的忠实性、完整性探针、状态和可携带性，不能证明下游一定实现正确，也不作为必须补做真实开发才能完成本方案的门槛。

## 11. 取舍与未收敛边界

- 不增加原子规则层和第二份功能描述；更细证据只作为引用绑定保存。
- 整份统一交付可能让一个局部冲突阻断全包，但一期不具备可靠的部分交付边界证明，因此先保留单一路径。
- 独立正反向及关系审计增加模型成本。实施时记录各类调用和失败用量；没有稳定同版本对照前不承诺成本下降。
- 跨功能关系仍依赖语义识别，证据齐全、复核通过均不能构成数学完备证明。固定反例和产物反查用于暴露缺口，不宣称百分之百无遗漏。
- 图像定位和转录有独立能力边界；整图引用可用于查阅，但不能冒充句级证据。无法判定的内容保持未检查或问题状态。
- 本轮没有运行真实模型或修改业务代码；本方案中的接口、状态、交付目录和验收条目均为待实施设计。
