# 阻塞事项建议方案

日期：2026-09-13。状态：已实施。

## 目标与当前实现

平台收到定版 PRD，即将交给开发 Agent。每个展示为阻塞的待处理事项，需要让用户看到具体处理建议、推荐理由、影响及需要决定的内容；用户能批量处理，继续使用同一个自然语言调整入口。

当前 `src/ResultIssues.tsx` 展示问题、已知事实、影响和依据。`src/types.ts` 的 Clarification 没有阻塞事项建议模型，defaultResolution 专用于建议级别的既有默认口径。`electron/scheduler-v2.ts` 的 clarificationSchema 也不生成处理方案。不能将新增建议塞进 defaultResolution，避免未确认的提议被当成既定规则。

业务阻塞仍不阻止生成交付包。平台整理事项目前也显示红色“阻塞”，因此应提供具体平台修复步骤，不将其包装成用户业务选择。

## 交互选择

| 方式 | 决定 | 理由 |
| --- | --- | --- |
| 每项打开弹窗回答并提交 | 排除 | 大量事项时重复操作，违反统一反馈入口的使用目标 |
| 所有建议都写进一篇汇总报告 | 排除 | 阅读建议时难与对应问题、依据及影响对照 |
| 每项正文展示建议，统一批量采纳或文本调整 | 采用 | 便于连续阅读，既能少量选取，也能一次说明多项例外 |

保持现有单列工作台、中文字体、语义颜色和依据抽屉。阻塞事项首屏显示：

```text
□ [阻塞] 安全合并时，空字符串或纯空格是否按 NULL 处理？
已知：NULL 有明确判定规则，非空值按原始存储值比较。
建议方案 [待采纳]：仅 NULL 为空；空字符串和纯空格保持原值参与比较。
推荐理由：沿用现有比较规则，不额外加入数据归一化。
影响：NULL 与空字符串不会被判为相同，可能减少可合并候选。
需要决定：是否允许上述差异存在。
[加入本次调整]  [查看依据与备选]
```

这是依据当前任务记录构造的设计示例，实施时必须重读固定原文才能形成正式建议。建议正文通常 2–4 句，必须说清处理规则；禁止只写“建议明确规则”“与产品确认”或“按最佳实践”。原文引用和较长备选理由放入已有依据抽屉，不能把推荐方案本身藏进抽屉。建议状态称“待采纳”，避免与“建议”事项级别混淆。

默认按影响本期的阻塞优先排列；仅影响本期不做的事项仍可阅读、生成建议，默认批量范围不包含它们。保持用户主动选择的筛选。

## 每项建议必须包含什么

1. 具体方案：采用什么规则，在什么条件下执行，用户可直接判定接受或修改。
2. 推荐理由：关联哪些原文事实、用户已确认口径，为什么更符合当前需求；不添加伪造的“行业标准”。
3. 影响与代价：改变哪些行为，有哪些明确的取舍，影响哪些功能与需求。
4. 待确认内容：明确指出相对于 PRD 新增或改变的业务决定。
5. 可选备选：有真实取舍时给 1–2 个有意义的备选；不强迫每题凑多个答案。
6. 依据与适用条件：相关来源、当前结果版本及与其他决定的关系。内部 ID 仅用于关联，页面显示业务名称。

确实缺少外部资料时也必须给出具体处理路径。例如“需要提供现行字段空值规范中的空字符串处理规则；取得后统一调整候选查询和执行校验”；说明缺什么、用于什么、可以先完成哪些无关部分。此类路径标为“需补充资料”，不能通过采纳操作假装已经回答未知规则。

## 生成及核查流程

有限的现有阻塞清单 → 读取各项相关原文、需求及有效用户决定 → 判断是否真有未决业务问题 → 生成建议或明确的资料补充路径 → 核查事实与提议边界 → 持久化并展示。

- 已有明确依据能解决的问题：修正相关需求并通过核查后关闭该问题，记录依据；不能直接修改状态，也不要求用户再次决定。
- 真正缺失或冲突：生成待采纳的业务方案；不得因为推荐了某个答案就关闭问题或降低级别。
- 平台处理失败：建议写明应修正的内容和核查步骤，由平台执行；不让用户采纳无依据结果。
- 资料缺失：指出具体缺失资料与用途，保留未决状态；不捏造阈值、权限、费用、接口约定。

真实例子：T-DD1D9FB1 的记录称主 PRD 明确“合并结束后打开独立生成版本确认弹窗，确认合并不触发版本生成”，原型按钮却叫“确认合并生成版本”。回查两处原文和材料优先级后，若行为没有真正冲突，应落实 PRD 的两步流程并修正文案；若两份材料同等权威且行为冲突，才提出两步流程的待采纳方案并展示冲突。不能仅依记录摘要自动裁决。

建议阶段面向已有阻塞事项，不恢复全文穷尽补漏。按真实关联的决定分组，同一来源只传一次，相关需求只保留必要字段；复用现有并发、提示预算、任务计量和检查点。稳定内容按依赖指纹复用，失败只重试受影响组。首轮在最终事项形成后生成；已有任务提供“生成建议方案”，不重跑全部细化。单项失败要显示原因与重试入口，不能卡住整个结果或假装已有建议。

## 批量采纳与统一输入框

- 事项复选框表示本次选择；提供全选本页及选择当前筛选全部，显示准确数量，不默认替用户选中。
- “加入本次调整”将该建议作为可移除的引用加入现有任务级输入区，保留已有草稿，不立即执行。
- 批量动作“按所选方案调整（N）”明确表示用户采纳当前看到的具体建议，可直接提交一次调整，不弹出 N 个确认框。
- 用户可在同一输入框写“这些建议都采纳，但空字符串按 NULL 处理；版本生成保持二次确认”。明确的文字例外优先；范围歧义只询问缺失部分，其余独立意见继续处理。
- 批量选择绑定事项、建议版本和具体正文快照。用户说“全部采纳”时绑定当前可见的建议范围，不含未来新生成的建议；只显示问题但尚无建议的事项不能混入。
- 互相冲突或存在前置决定的建议，先展示具体冲突；不能顺序覆盖。属于同一决定的变更作为一个整体核查和发布。

采纳后：持久化用户动作及所采纳建议全文 → 定位受影响功能 → 复用现有局部调整路径 → 核查需求与依据 → 发布结果版本 → 回报已落实、仍需补充、未成功数量。

点击采纳只是授权采用建议；只有相关需求已实际更新并通过核查，事项才能关闭。处理失败保留原问题、原结果和本次输入。不得只向输入框插入“采纳第 X 条”后让后台依据一个可能已变化的建议自由推断。

## 状态、版本和交付

建议与事项是两套状态：事项仍是未解决、已解决等；建议可以是生成中、待采纳、需补充资料、生成失败、已失效。提交调整后的落实情况沿用调整结果，不用“已采纳”冒充“已解决”。

原文、相关需求或用户决定变化时，旧建议保留为历史但失效，禁止基于过期方案直接提交；未变化的建议可继续复用。保存依据引用和依赖指纹，不因刷新页面重复生成。应用过程沿用任务族版本冲突和幂等控制。

交付 JSON、Markdown、Excel 同步展示推荐方案和待确认状态。未采纳方案留在待处理事项中，明确标记“仅供参考，尚未确认”；不能作为已确定需求流入 Agent 的执行规则。用户采纳且落实后以可追溯的用户决定作为新依据。待处理事项非零仍可交付。

## 实施落点与验收

复用 Clarification 的来源和影响范围，增加独立的建议结构；复用 ResultIssues 的列表和依据抽屉、TaskFeedback 的统一输入、refinement-adjustments 的局部调整及 scheduler 的任务恢复，不新建独立审批页或第二套调度器。实施时同步 README、DESIGN、UX 契约和导出说明。

必要验收：

- 每个红色阻塞事项都有具体方案、具体资料补充路径或明确可重试的生成失败；没有空泛占位建议。
- 原文已有答案的例子先回查并落实，不重复要求用户确认；真正缺口明确标注为提议。
- 80 项事项无需打开 80 个弹窗，批量选择加一段例外说明可一次提交；同一功能不会逐题重复细化。
- 生成建议不改变已确认规则；采纳失败不关闭问题；冲突与失效建议不能静默应用。
- 同一业务决定关联多项事项时一致处理，无关同名对象不误改。
- 交付包保留未采纳建议的未确认标记，不把它们写入正式业务规则。
- 真实 Electron 检查长方案、加载、失败重试、批量选择、依据抽屉、输入草稿、过期建议和 1100px 布局；截图必须逐张查看，不能仅凭脚本退出成功宣称 UI 验收完成。

本轮仅形成设计，没有调用模型生成正式建议，也未修改用户任务或应用代码。
