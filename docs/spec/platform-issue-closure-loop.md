## 原因链

### 1. 完成条件是阶段函数返回，不是平台问题关闭

`electron/scheduler-v2.ts:260` 的 stage 只要 work 返回就标 completed；`:545` 调用 graph 后没有检查返回的 uncovered；`:551` 无条件将任务标为 completed。assessDelivery 只把产物分到 drafts，不阻止任务显示完成。正式交付包仍被拦住，但用户看见的成功语义错误。

`tests/scheduler.spec.ts:127`、`:133`、`:182` 明确断言修正失败或未分类问题仍为 completed。因此原测试绿是验证了旧行为，不能证明业务闭环。

### 2. 修正只有一遍，失败也会排除后续调度

`scheduler-v2.ts:508` 只生成一次局部修正计划；复核不通过只记录 rejected，不把 verification 反馈给下一轮。`:536` 无论接受或拒绝都写 repairIssueIds，下次过滤时跳过。功能边界仅有一次机会，检查不通过、没有变化或预算耗尽均直接退出返工。

另有重试边界错误：模型响应结构校验在 ask 内，候选图的 applyRequirementPatch 预检查却在其外（`:516`）。本次三条系统记录声称“连续两次”，实际每个对应修正范围只有一条 try1 模型调用，预检查失败没有获得定向纠正机会。

### 3. 审计拿不到相关的全部业务内容，造成误报和重复新增

`scheduler-v2.ts:442` 只按同一 sourceUnitId 检索需求。PRD 概要、正文、验收标准重复描述同一行为时，需求可能绑定另一处原文，当前包会错误看到“没有需求”。A-0005 报筛选和全选未承接，但 R-0005 已有这些行为；A-0007/A-0015 称“能够操作当前版本”无依据，而正文与 AC-14 明确写了该条件。应区分证据绑定缺口与无依据的业务内容。

局部复核只带修改条目和极少的只读需求，不能识别另一批已补好的相关行为。A-0003 的候选被要求补上独立确认版本生成，而 A-0004 已在另一个修正范围承接该部分；不是所有拒绝都证明候选本身错误。

### 4. 来源缺口扩大为整功能重写，破坏了定点修正

`electron/audit-repair.ts:56` 在问题指向 F 时把该功能全部需求设为可写；共享写集合再传递合并。本次 46 条来源覆盖记录以 F 为 affectedIds，促成一个 58 问题的大批次。`:131` 又将全部读取来源视为本批必须消除的缺口，包括只作为上下文读取的来源。局部内容正确仍可能因无关缺口整体拒绝。

### 5. 提交后没有刷新问题与派生结果

源码只把当前 scope 的 issue 标为 repaired，未重算其他覆盖记录、重新审查重叠问题。已有 16 条过期未覆盖记录证实该问题。旧审计缓存按批次是否存在复用，没有绑定当前需求/关系版本。关系失效时只新增 requirement-relation 问题（`:526`），本轮计划不再处理；多功能归属不唯一和未分类问题还可能被跳过。

### 6. 平台元数据和重复执行生成了假业务问题

`document-assets.ts:103` 将 label 截到 100 字符；模型仍能看到该标签并拿它与证据正文比较，形成 Q-0002。`attachAuditClarifications`（`scheduler-v2.ts:123`）首次关联后删除 clarificationDraft，再次调用却把没有 draft 当成整理失败。本次 A-0023 已有 Q-0003，仍被改成 runtime-output/open。

## 方案比较

| 方案 | 判断 |
| --- | --- |
| 只改任务文案或隐藏平台事项 | 不能解决遗漏和返工失败；不采用 |
| 增加次数或重复提交整个功能 | 过期问题、错误证据、范围过大仍在；容易循环与重复需求，不采用 |
| 失败后整份 PRD 全量重跑 | 丢失已验证成果，并把随机生成风险扩大到全部结果；不作为默认修复 |
| 校准问题 + 按责任节点修正 + 独立复核 + 刷新当前结果 | 推荐；沿用现有八节点，不增加另一套分析流程 |

## 推荐流程

### A. 细化时就区分缺内容与缺引用

每个功能产出后，先做结构检查和该功能的内容检查，形成可定位的内部修正项：

- 原文已有要求、当前需求未表达：补充既有需求的字段，确实独立的行为才新增。
- 行为已经表达、当前出处未绑定：选证据并校验支持关系后补绑定，不复制一条同义需求。
- 功能归属或来源分类错：退回候选/统一责任节点。
- 原文有真实不可决定点：整理成可回答的三级业务澄清；不能让澄清代替同段中已明确的要求。

审计工作集至少包括当前原文包、所属功能的相关需求、适用约束、现存问题和已关联澄清；按需扩展到跨功能相关条目。反向审计拿到待审需求的全部证据，避免仅凭当前段落断言“无依据新增”。宽泛功能超出预算时按业务对象/场景切包，建立全量审查清单；检索未命中不能当作确定遗漏。

label 只用于导航，不能作为业务证据进入判断；模型只读取完整冻结证据及明确的结构上下文。解析出来的标签、省略号和系统文案都不是另一份 PRD。原型与正文是否冲突应结合 PRD 自身的优先级约定判断，不自动假设所有原型差异都是业务未决。

### B. 节点 6/7 形成有界闭环

顺序为：当前快照审计 → 问题校准与归类 → 生成本轮工作项 → 独立范围并行修正 → 候选预校验 → 独立复核 → 串行提交 → 刷新受影响范围 → 重新判断剩余问题。

每项问题必须能观察到：待定位、待修正、修正中、待复核、已修复、有依据排除、已转为业务澄清、修正失败。只有后三类成功处置中的“已修复、有依据排除、已转为有效业务澄清”算关闭；尝试次数独立保存，不充当完成标志。保持稳定问题身份，绑定所检查的结果修订；修复后复发应重新打开，而不是生成另一个无关联编号。

所有失败都回到对应责任：

| 反馈 | 下一步 |
| --- | --- |
| JSON/证据/候选图校验失败 | 在同一修正调用边界反馈精确错误、允许证据和必需覆盖范围；实际调用几次就记录几次 |
| 原问题未解决 | 将独立复核反馈加入下一轮同范围修正 |
| 复核发现新的业务疑问 | 核实原文后进入澄清路径；不因与当前修正无关的问题无差别拒绝全部候选 |
| 归属或分类不确定 | 内部定位到候选/统一节点，不能 silently skip |
| 修改影响需求关系 | 调度对应关系复核，更新证据与关系；不能只留下一个待处理标签 |

建议首版每个稳定问题范围最多 3 轮实质修正，单次输出校验维持最多 2 次；两轮针对同一输入/问题没有经复核的进展则停止重复调用。轮数、时间/调用预算和每轮反馈持久化；断点恢复不重跑已经验收的独立范围，不重置预算。超限后保留成果和诊断，将任务置为“平台整理未完成”，不能变成 completed。成功指标是具体义务被满足，而不是问题总数下降或被改了分类。

### C. 缩小写范围，扩大必要阅读范围

来源缺口不再默认授权改写整个功能。工作项明确：本次必须解决的来源/规则、允许修改的需求及字段、允许新增的业务行为、只读上下文。共享来源可以并行；修改同一条需求则排队，读取最新版本继续，不因共享一条需求把全部问题传递合并为大批次。单条需求确实过大时先分析合理拆分，不按字符任意切开。

候选必须解决本次指定缺口，并且不能破坏原先已覆盖的内容；只读上下文中的其他既有缺口由对应工作项处理。其他义务不会因本批不负责而被删除，最终全局检查仍需全部闭环。

提交前检查读集和写集修订。无冲突的结果串行分配编号并提交；读取的业务内容已被另一批改动时，重新复核该候选。不要把过时的复核结果直接写回最新项目。

### D. 提交后刷新，最终再验当前快照

每次接受修正后，重算结构缺口，对当前已具备引用的历史结构问题销账；这只证明该引用义务解决，不自动关闭相邻语义问题。对改变的需求、共享约束、关系和澄清，清除对应旧审计缓存，重新复核后更新问题状态。有效 clarificationId 已存在时保持关联，多次调用不得反向生成平台故障。

最终检查必须使用同一个当前结果版本：平台开放问题为 0、明确来源义务全部承接、所有必要审计通过、关系/澄清无悬空、没有结果版本变化后遗留的旧验证。通过后才生成正式包或等待业务澄清的审阅包。草稿可保存进度，但草稿生成不代表任务成功。

### E. 用户看到的状态

| 当前情况 | 用户状态 | 用户动作 |
| --- | --- | --- |
| 平台仍有可执行修正 | 正在整理 / 正在复核 | 无需回答平台问题 |
| 平台修正耗尽预算、调用失败或缺乏充分验证 | 平台整理未完成 | 保留草稿；显示实际失败范围和具备执行路径的恢复入口 |
| 平台问题已全部关闭，仅有真正 blocking 业务问题 | 待你澄清 | 回答具体业务决定 |
| 平台检查通过且无 blocking 业务问题 | 可交付 Agent | 建议、可忽略事项随包展示 |

阻塞、建议、可忽略继续描述业务澄清级别。平台责任问题属于执行状态，不能靠标成“可忽略”放行，也不能提示“将自动重新整理”却没有实际调度。

## 实施与恢复顺序

1. 先修完成判定、实际重试计数和误报；重写将未解决平台问题断言为 completed 的测试。
2. 修审计工作集和问题归类，加入补证据路径，验证重复原文不会制造重复需求。
3. 把局部修正改为有界反馈循环，加入小范围计划、结果修订检查、关系复核和澄清幂等关联。
4. 修正提交后的重新审计和最终准入，接入用户状态及恢复入口。
5. 新协议升级检查点版本，不能直接继承旧版 repairIssueIds=已完成的假设。对本任务重新解析并审计当前结果，重新验证证据后分类处理历史问题，保留有依据的已有成果；迁移不可验证时用冻结输入重建，不能直接改 JSON 把问题清零。

## 验收

- 有未关闭平台问题或 30 个未覆盖来源时，任务不得成功完成。
- 结构校验通过但预应用失败也会收到真实失败反馈，计数与模型调用一致。
- 复核拒绝后仍进入下一轮；达到上限显示未完成，重试不跳过所有未关闭问题。
- 58 问题样本拆成有明确目标的小范围；共享写目标串行，不强制整功能重写。
- 原文多处重复提及同一行为时，优先修证据关联，不新建宽泛重复需求。
- 16 条已有覆盖记录正确销账，但剩余语义问题仍需独立复核。
- `Not Calculate` 截断标签不会形成业务澄清；Q-0003 已关联后重复处理仍保持一致。
- 局部修正发现新问题、引用跨批修改、关系失效和未分类责任均有后续调度或明确未完成状态。
- 当前真实 PRD 的平台事项清零必须逐项有修复或排除证据，不能只看关键词、进度 100%、测试全绿或问题数量。

可以保证的是平台不会带着未完成的自身问题宣称成功；不能保证生成模型在有限预算内修好所有输入。真正的原文未决点依然应由业务人员决定。
