## 程序根因

1. 路由使用两套分类：`scheduler-v2.ts:587` 按 category 选择功能返工；`audit-repair.ts:44` 同时限定 category=detail-mismatch 和 owner=requirement-detail。冲突分类可选错处理器，其他 owner 可无人处理。
2. 来源覆盖与业务要求混淆：标题被标记 requirement 后，`audit-repair.ts:134` 的覆盖约束强制新增承接；修正协议不能更改来源处置。生成标题需求被语义审计拒绝，返回空补丁又被覆盖门禁拒绝。
3. `scheduler-v2.ts:690` 的三轮是全局循环，不是每个新问题的完整处理机会。第三轮发现的问题可以直接留到交付门禁。
4. `scheduler-v2.ts:723` 以完整 scopeKey 查 previousAttempts。同一对象的问题集合变化，scopeKey 随之变化；R-0047 的三个尝试使用三个 key，前次复核反馈不能按同一问题连续继承。
5. 确认/复核按整个功能目录分片；修改仅取同源相关内容，两者语义上下文不对称。标题修正看不到章节正文，复核却能看到并否决。
6. 539 次尝试中，成立性确认 148 次，局部复核 111 次，局部修正 25 次。问题与需求分片交叉遍历造成调用放大；调用数量不等于修复进展。

## 方案

采用问题工作队列，替换固定三轮串行阶段。保留现有调度、检查点和补丁机制，不新建另一套平台。

1. 每条平台问题必须有唯一有效处理动作：来源处置、来源绑定、需求明细、功能边界、需求关系、澄清纠正。问题注册时校验目标和处理器，禁止无处理器仍继续推进；真实业务未决与平台澄清纠错分开。
2. 先核实问题，再生成补丁。来源缺引用不能直接判内容缺失；章节标题是否承载独立规则需结合正文判断，不能一刀切丢弃所有 heading。纯结构标题可以修正为 context，仍保留来源和导航。
3. 修正与复核共享同一最小完整业务上下文：相关正文、必要章节上下文、关联约束、当前成果、已确认缺口。按预算拆包，但完整问题只由具备所需证据的包裁决，其他包仅检查受影响部分。
4. 对 R-0047 这类问题输出字段级修改意图与证据选择；程序检查指定缺口是否真的改变，未改变直接记录无进展，不重复调用全功能审计。不能仅把所有可见来源挂上去冒充语义支持。
5. 所有阶段新发现的平台问题重新进入队列。按稳定问题身份及目标对象保存尝试和差异反馈，不以一组问题的临时集合键隔离历史；分组改变不丢失反馈。
6. 同一缺口重复且输入/动作未变化时停止盲重试，进入重新分类、补齐上下文或针对性增强处理。仍无法处理时明确记录技术失败原因；无总时限不意味着无进展无限重试。
7. 只使受修改影响的检查失效。队列为空、所有平台问题关闭且当前版本的检查有效，才完成平台整理；真实业务未决单独保留。
