输入是定版 PRD。产物可以调整粒度，可以追加明确业务决定；不定义需求识别完整率，不重启全文补漏或穷尽审计。核心要求是当前业务主张、澄清及已处理决定有依据，变更后引用、版本、状态和交付一致。

## 方案选择

| 候选 | 结论 | 原因 |
| --- | --- | --- |
| 在各入口分别补状态判断、引用检查和导出调用 | 不采用 | 两套生成路径继续独立演化，同一主张在首轮和调整时受到不同检查 |
| 所有调整恢复全文重跑和完整性审计 | 不采用 | 违反按需调整目标，重新引入长耗时和旁支返工 |
| 共享按功能生成、依据核查、版本发布路径 | 采用 | 初次与全量只多做材料读取和功能整理，局部操作只改变输入范围 |

## 一条执行路径

提交调整并保存输入 → 进入现有调度队列 → 构建冻结范围输入 → 生成候选 → 依据核查 → 必要时一次修正及复核 → 引用校验 → 版本提交与产物发布。

初次生成和全量重生成在前面执行材料读取、功能整理；功能调整、澄清回答和局部补充从范围输入开始。main 只校验请求、持久化并入队，立即返回执行记录，不在 IPC 中等待模型结束。

复用 AnalysisTask 保存执行、输入、候选和检查点，不再把一条 completed 记录同时当作执行过程、检查证明及交付文件存在的证明。执行记录引用父结果；只有发布成功才分配正式 resultVersion。

## 输入、状态与恢复

1. 操作准入基于“是否有可查看的结果及有效目标”，允许已整理但有阻塞澄清或局部待核查的结果继续调整。没有有效结果的运行失败走故障重试，不伪造可调整范围。
2. 用户原始文本、操作类型、关联问题或功能、来源版本、提交时间在模型调用前保存。区分粒度指令、补充事实、澄清答案和不适用决定；不把 UI 自动拼接的提示语当成用户事实。
3. 用户输入提交成功只表示已保存；界面分别显示等待生成、正在生成、已应用、应用失败。失败重启可读取输入、原因和候选，不要求重填。
4. 粒度指令在所有后续路径中都不能作为业务证据，不能仅在本轮检查 businessFact。有效业务依据包括 PRD、正式补充、明确决定；下一次调整也必须携带仍适用的历史依据。
5. 用户说明与 PRD 冲突时保留双方依据；用户明确指定替代的原规则才被取代。纯“更细”“更简洁”不得新增业务事实；不适用决定需明确目标和说明。
6. 沿用当前任务冻结材料建立补充草稿，不读取同名资料包最新版本。文本、附件、替换主 PRD 经已有材料索引形成新输入；替换主 PRD 走全量重生成。
7. 同一次执行的重试复用 input、operationId 和有效检查点。新修改另建请求；取消与迟到模型结果不能越过提交校验。

## 产物依据核查

结构校验与语义核查分开：结构校验确认来源存在、版本和选区有效、字段绑定合法；语义核查检查当前产物的主张是否受证据支持，是否改变否定、条件、例外或适用范围，以及当前澄清是否确实未决。

按目标功能读取它的来源、适用公共约束、关联需求、相关问题与有效用户补充；核查须有这些关联上下文，不能仅回看模型自行选择的有利引文。只核查已有主张与当前决定，不对全篇寻找未识别需求。

无依据主张拒绝候选；最多一次针对性修正与一次复核。结构纠错预算与语义修正预算分开且都跨重试持久化，用户手工重试不能重置自动预算。修正后仍未通过或模型核查失败，记录该范围待核查，保留可查看结果，不转成“PRD 缺失”的业务澄清。

初次生成按功能隔离生成、核查及修正失败。其他功能继续产出；跨功能已有关系或公共约束影响的范围须正确标记。局部调整只有目标范围通过才替换对应正式内容，不能用未经核查的新条目覆盖旧结果。用户已明确修改的规则涉及的范围显示待更新，交付时不得把该范围旧内容当成已经应用新决定。

证明绑定实际业务内容、引用及适用依据的指纹。未变功能沿用仍有效的检查结果，不因全局版本号改变强制全量复核；受变更影响的证明失效。语义检查通过不等于数学意义的无幻觉保证。

## 澄清必须显式处理

生成输出要分别表达需求变更和问题处理动作，不能以未返回某问题表示删除。

- 保留：尚无唯一业务结论，原问题继续开放。
- 更新：根据补充收窄或改写未决点，保留身份与历史。
- 解决：指出答案或原文依据及承接结果，由核查确认原问题已经得到处理。
- 不适用：根据用户明确决定关闭，保存原因与来源；不强行创建一条需求作为销账凭证。

“解决”不能只检查用户来源 ID 出现过，也不能只因模型返回结构合法而通过。答案与需求表达相矛盾、回答没有落实、仅补充背景仍有未决点，均不得销账。一个决定涉及多个功能时先核查全部受影响结果，再提交一次问题状态，禁止重复插入相同 Q。

普通粒度调整保留与本次变更无关的问题。共享来源不意味着可以删除其他功能的问题；任何问题删除、合并或替代都要求显式动作与依据。

## 编号、关系与版本

需求输出明确 create/update/delete；update 显式指向原 ID，不依赖数组顺序。拆分、合并显式列出被替代条目，新增条目由程序分配唯一 ID。不能机械地把旧关系挂到拆分后的第一条需求。

对变更涉及的关系和澄清引用做定向重绑定；无法确定关系去向则保留明确待核查问题。发布前执行程序图校验：编号唯一，引用存在，所属功能一致，外部引用没有静默改换业务对象。无需借此重新核查全篇语义完整性。

版本发布使用任务族的当前正式结果作为基准：
1. 提交时检查 baseResultId，防止在历史版本上直接提交。
2. 发布前在同一任务族短临界区再次核对当前正式结果。
3. 第一个成功请求发布 N+1；另一个仍基于 N 的请求保留输入与候选，提示基准已改变，不自动覆盖或合并。
4. 用户选择在最新版本重做时才生成新请求。普通故障重试不能暗中改变输入基准。
5. 使用 operationId 实现重复请求幂等；同一执行恢复不能分配第二个正式版本。

沿用现有原子文件保存和 scheduler 写入队列；补任务族级提交互斥及基准比较，不引入通用事务框架。正式任务文件作为结果发布完成的唯一入口。临时产物先完整生成并回读，最终原子保存引用它的结果记录；中途崩溃从已保存阶段恢复，未正式发布的目录不能被 UI 当成有效交付。

## 展示与交付

执行状态表示生成是否结束；功能状态表示依据是否核查通过、是否有阻塞决定；交付状态表示用户选择的范围是否可以生成执行包。页面“整理完成”不再等于全项目可交付。

一个功能仍阻塞时：该功能可查看、回答和调整；无关且已核查功能可选中交付。用户选择交付范围后，程序沿显式业务关系和公共约束检查依赖：依赖受阻的范围不能宣称无关，也不自动加入未经选择的业务范围。无法确定的联系显示待用户决定，不推测所有语义影响。

人工审阅导出可包含全部结果和待处理项，并明确是审阅稿。开发 Agent 包的执行性 requirements 仅包含获准范围；其余放在独立待处理清单，不混在可执行需求中。JSON、Markdown、Excel、manifest 使用同一不可变快照、结果版本和范围。

调整必须重新计算当前交付状态、inputHash、resultHash，禁止继承旧 delivery。生成文件并回读后才显示“已生成交付包”；失败显示具体导出状态，可从同一结果重试导出，无需重新调用模型。结果差异保存并展示新增、修改、删除、澄清处理及依据变化。

## 提示词与并发

所有调用经现有 runtime adapter、节点配置、槽位及预算工具。保持最大任务数默认 5、单任务节点并发默认 10；同一任务族发布串行，不影响其他任务并发执行。

按完整请求测量 Token：目标来源、适用约束、需要变更的当前需求、问题和有效补充；排除无关功能和历史执行日志。输入及核查都按预算分批，单个主张证据过大时复用已有联合证据分片能力。不得截断条件或使用摘要代替证据。

持久化排队时间、实际调用模型、调用时长、提示长度、输入输出 Token 和重试原因。20 分钟仍是性能观察线，不是任务总终止限制；单次调用故障超时保留。

## 验收与反证

先逐项迁移被整组跳过的测试：取消、恢复、密钥、引用、并发、预算等仍有效的保留并适配；穷尽补漏和反复全文审计断言删除，换成“不会调用这些节点”的反向断言。不得保留整组 skip 作为通过依据。

必须实跑以下反例，记录于现有 acceptance 的 matrix.csv 与新 round 文件：
1. needs-attention 状态回答阻塞问题，输入保存、候选引用答案、核查后销账；原问题仍未解决时保持开放。
2. 999 元手续费引用真实但无关原文、答案已挂来源但业务含义相反，均被拒绝；两段联合支持的结论可通过。
3. 展开、精简和重排不产生无依据规则，不删除无关澄清，不改变其他功能。
4. 粒度指令在后续全量重生成中仍不是业务证据；旧有效用户答案和公共约束不丢失。
5. 拆分、合并、删除后关系与澄清引用有效，无法重绑的范围不会被当成可执行内容。
6. 两个请求基于同版提交，只发布一个后继版本；另一个保留候选并提示冲突。重复发送相同请求、提交阶段重启，不产生重复版本。
7. 模型失败、取消、应用重启后输入可恢复；迟到响应不能提交；故障重试不重置修正预算。
8. 单功能生成或核查失败，其他功能可查看；只有被确认无关且已核查的范围可交付；显式依赖被阻塞时不能漏判。
9. 新版本显示的交付状态与真实文件一致，三个格式范围一致、哈希对应本版；导出失败可独立重试。
10. 大功能调整经过真实预算分批；多个任务共用并发上限；无全篇补漏调用、无自动预算重置。
11. 替换主 PRD 或补充材料基于冻结版本形成新输入；页面展示差异和历史结果，失败不覆盖历史。

结构测试验证确定性不变量；冻结反例和真实模型运行验证核查质量，二者分开报告。最后在 npm start 启动的真实 Electron 上走首次生成、功能调整、回答、补充全量生成、失败恢复、范围导出，并分别记录耗时及提示长度。未完成这些证据前，不能以构建成功、进程启动或单元测试通过宣布新方案完成。
