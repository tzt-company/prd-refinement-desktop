# Runtime 执行性能优化

## 目标

在不改变来源原文、来源编号、节点职责和 fail-closed 校验的前提下，减少重复提示词内容，并让墙钟耗时、模型活跃耗时和人工等待重试时间可以区分。

## 当前证据

- 任务 `T-61E0C5FB` 共 375 个来源单元、47 次逻辑调用和 55 次实际模型调用。
- F-001 细化输入包含 217 个来源单元；原文摘录约 7 千字符，重复结构上下文约 7.7 万字符。
- 8 次结构或引用校验重试额外产生约 38.7 万输入 Token。
- 47 分 23 秒墙钟时间中约 27 分 13 秒位于两次执行代次之间。

## 方案

1. 提示词序列化时，将相同的来源上下文提取到 `sourceContexts` 字典；各来源单元以 `contextRef` 引用。来源 ID、原文、位置、角色和资产文字保持原值。
2. 保留完整节点 JSON 的有界二次校验重试。现有逐字引用误判修复会直接消除本任务细化节点的对应重试；其他重试继续 fail closed。
3. 从真实调用时间区间计算模型活跃耗时，从执行代次边界计算等待重试时间。界面继续保留墙钟耗时，同时明确三者含义。
4. 用真实任务快照对压缩前后的 JSON 长度做确定性验证，并运行调度器、界面、类型检查和构建测试。

## 验收

- 展开 `sourceContexts` 后，每个来源单元的上下文与压缩前逐字一致。
- 重复上下文只在请求中保存一次，真实任务的细化输入体积明显下降。
- 逻辑调用次数、检查点、来源引用和模型输出契约不变。
- 成本区域显示模型活跃耗时；跨执行代次存在等待时显示等待重试时间。
