# 任务级自然语言批量调整

2026-09-13。已实施。用户否定逐条打开需求或澄清填写的交互，本方案替代 evidence-led-requirement-refinement.md 中的三个独立调整表单；既有证据、预算、版本及范围交付约束继续有效。

## 真实场景与问题

用户拿到一批需求和澄清后，通常形成一段审阅意见、会议结论或统一业务口径，需要一次处理多个对象。平台已经掌握 PRD 和当前产物，不应再要求用户逐项定位、选择操作类型和填写关联关系。

当前证据：App.tsx:50-51 每个功能单独打开调整抽屉，要求选择方式或范围；ResultIssues.tsx:44-49 每个问题单独填写答案及处理类型；types.ts:200 的请求只有单个 featureId、clarificationId；refinement-adjustments.ts:39 根据操作类型要求显式处置，:108 根据单目标定位功能。现有任务级补充默认全量重生成，不能承担混合意图的批量调整。

候选方案比较：

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| 将全部澄清铺成可编辑表格 | 不采用 | 少了开关抽屉，仍要求用户逐题填表；无法自然表达跨功能的统一决定 |
| 先勾选多个条目，再选择批量操作 | 不作为主路径 | 用户仍需遍历和定位；可作为可选引用辅助，但不能成为执行前提 |
| 一个任务级输入框，平台定位并批量执行 | 采用 | 用户一次表达意见，平台承担目标匹配、范围分配和相关事项更新 |

## 用户主路径

结果页统一提供“描述你希望怎么调整”多行输入区；功能、需求、待处理事项标签共用同一草稿，切换不清空。默认只展示输入框、展开输入区按钮和“按说明调整”主按钮。移除调整方式、处理方式、更新范围等前置选择，不要求填写编号。沿用当前中文字体、颜色与结果阅读布局，输入区位于结果页上部，可展开成长文本编辑区域，不覆盖列表。

输入支持一段话、多条意见或粘贴会议结论；同一段内允许混合颗粒度要求、纠错、业务补充、澄清答案和不适用决定。例如：

> 订单查询细化得太碎，同一组筛选条件合并描述；退款审核按发起、审核、完成展开。退款金额一律含税，相关澄清按这个口径处理。支付超时先保留，其他内容不动。

用户输入并提交一次，平台保存原始文本、定位受影响内容、完成依据核查并生成一个结果版本。无需逐条点选映射结果或审批每条改动。执行中的状态、完成后的结果都显示在本任务内；列表仍是业务产物的主体。

一项明确的调整默认直接执行。只有指代不清、输入相互冲突或缺少决定行为的信息时才追问，且只列真正缺少的内容。例如同名“审核”同时对应退款审核与发票审核时，展示两个业务名称并让用户补一句。回答仍使用同一个输入区，自动关联这次待确定的请求；不重新要求填写整个批次。

只有查看证据或差异时才需打开条目详情。可选的“引用到调整说明”只将用户看到的对象加入同一输入区，不启动另一套表单，也不限制用户继续描述其他对象。

## 大量澄清如何阅读和处理

保留阻塞、建议、可忽略分级，默认优先展示阻塞。每行直接显示具体问题、已知口径和影响范围，原文证据按需展开。不要将关键问题藏在“查看详情”后。

确实属于同一业务决定的多项澄清，可聚合为一个阅读分组，显示影响范围和关联事项数；按名称或类别相同不能直接合并。分组不能销账，也不能丢失内部事项身份。一个答案可以覆盖多项澄清，平台核对每项是否已被解决；未覆盖的问题继续保留。

用户可以写“导出相关问题统一按下面的口径……”“这批关于错误文案的建议暂不处理”。暂不处理保持未决，不自动等同已解决；“全部按常规处理”不能凭空产生权限、金额或阈值。只有存在明确且有依据的默认方案、用户意图也清楚时才可采用该方案。

## 处理流程

保存原始反馈 → 定位对象并形成内部调整清单 → 按依赖分组生成变更 → 核查依据与关系 → 发布一个新版本 → 回报落实情况。

1. 请求入口只需基准结果、原始文本及幂等键；可选引用作为辅助。前端不再提交业务类型和单目标处置。后台将一段反馈拆成内部操作，每个操作绑定用户输入的实际文字区间、目标集合、依赖及预期结果。
2. 区分整理指令、明确事实、修改旧口径及待回答问题；分类用于平台执行，不变成用户必填字段。同一段内的“更详细”和“金额改为含税”分别处理，不能用整个文本的单一 businessFact 标志。
3. “改为”“以本次说明为准”等明确改口径可替代所指旧规则，并保留新旧依据；“是否可以改为”只是问题或建议，不能直接当成已确认的业务决定。解释含糊就列出需要确认的点。
4. 平台根据业务名称、需求正文、问题内容和可选引用匹配目标，不只按标题关键词。未明确指定全局的意见不静默扩大到全部功能。定位不明确时保留候选范围并追问，不挑第一个结果执行。
5. 每个操作读取相关原文、适用公共约束、当前需求、关系与有效用户决定。复用当前 runtime、队列、预算和版本发布，不增加独立运行器。先用产物目录定位，再读取完整的相关证据；不向每个节点发送全任务 JSON 或全部历史对话。
6. 同一决定影响的功能一起验证、一起提交；同一澄清只处置一次。相互独立的意见可并行，最终汇入一个新版本；有歧义的意见保留待确认，其余已通过的独立意见可应用。若用户要求全部一起改，则整批成功才发布。
7. 同一功能的多个意见在一次生成中执行，禁止每条意见各重跑该功能。局部调整不重跑无关功能；“全部合并精简”只调整已有结果的表达，不重做材料读取与功能发现。
8. 逐项核对本次用户意见是否已落实，这项检查面向有限的反馈清单，不恢复全文需求完整性门禁。无依据候选不能提交；失败、未解决或冲突必须可见，不伪装成已应用。

## 结果反馈与恢复

结果先展示“这次改了什么”：用户意见及其处理结果、受影响功能、需求变更和澄清变化。只有需要细看时才展开到逐条差异。例如“已落实 4 条意见，另有 1 处需要确认”，并写明那一处是什么。不能只报“生成成功”或展示一串 ID。

草稿自动保存；任务执行中可以继续写下一段草稿，但同一任务的修改按版本串行提交，提交时基于已固定的版本。失败保留原文、操作清单和完成检查点；重试不重做已完成工作。部分成功的结果以已应用、待确认、未成功分别反馈，不把待更新范围的旧规则冒充新决定已经生效。版本冲突不得静默覆盖。

历史版本可查看；用户可撤销本次调整，恢复上版内容并形成可追溯记录。只影响平台结果，不触发开发 Agent 执行。范围交付维持既有资格检查，独立于调整输入。

## 验收场景与反证

- 100 个功能、1000 条需求、80 项澄清的固定样本：不点任何需求或问题详情，一段输入同时修改三个功能并回答多个问题，只提交一次、生成一个版本。
- 同一问题在多个功能出现：输入一次口径，所有真正相关且已落实的事项正确处理，无关同名事项不变。
- 同一段既要求更细又补充业务规则：只有明确事实成为新依据，整理指令不产生业务规则。
- “支付超时暂不处理”：保留未决状态和交付限制，不能直接关闭。
- 目标名称有歧义：只询问具体指向，不要求重填其余意见，不误改其他功能。
- 输入含五条独立意见，一条无法处理：四条通过的意见可以应用，剩余一条明确回报原因；同一决定的相互依赖修改不得拆开成功。
- 切换标签、重启、失败、重试：输入不丢，不重复发布，历史版本可回查。
- 提示词按功能组和有效证据装箱，显示实际输入 Token、耗时；不以自动影响定位覆盖所有语义关联作为完成承诺。
