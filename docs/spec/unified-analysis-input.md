# 分析前后统一输入方案

日期：2026-09-13。状态：待实施设计；本轮只形成方案，不代表界面或处理链路已经修改。

## 1. 目标和依据

平台接收定版 PRD，产物用于交给 Agent 实施。用户应能在第一次分析前，同时提供文件和一段描述，包含背景、业务补充、范围调整、颗粒度要求、澄清结论。看到结果后，继续通过同一个输入方式提交说明、附件和采纳的建议，生成下一版。

可验证目标：一段混合说明只提交一次，相关内容一起处理；明确业务结论有用户原话作为依据，整理要求不会变成业务事实；没有采纳的建议不会自行生效；用户能看到本次实际使用的输入和落实结果。

当前代码依据：

- `src/MaterialWorkspace.tsx:67,84–97`：准备页调用资料包投影后创建任务，文件识别和分析分两次点击；尚无文字输入。
- `src/material-types.ts:16–21`：资料包保存文件、索引及进度，没有本次说明。
- `electron/material-bundle.ts:149–170`：项目从文件索引生成，已有文件及来源的快照机制，可以复用。
- `src/types.ts:198–225`：已有用户证据和任务级调整请求，可以延伸其职责，避免再建一套意见系统。
- `src/App.tsx:1327–1355`：结果页把自由输入和勾选建议拼接成字符串提交。
- `electron/scheduler-v2.ts:309–310`：采纳建议要求反馈包含原始推荐文字，用户修改后的推荐可能被拒绝。统一提交必须一起修正这一契约。
- `electron/refinement-adjustments.ts:281,576,825`：已有意见分类、局部落实、依据检查，可复用；首次分析要在功能识别前纳入用户说明，不能等结果生成后再补跑。

现有 `DESIGN.md` 约定两步识别/分析、760px 初始页和 1040px 准备页。本方案建议调整为同宽准备表单和一个开始动作；实施时同步修改设计契约与运行代码，本轮不改写现行契约。

## 2. 方案选择

| 选择 | 实际效果 | 决定 |
| --- | --- | --- |
| 在资料页加一个备注框，只追加到提示词 | 改动小，但无法保证首次识别使用、结果引用、修改建议和重试的一致性 | 排除 |
| 分成背景、补充规则、澄清、范围、粒度等表单 | 字段明确，但把意见分类和逐项关联工作交给用户，复现此前操作负担 | 排除 |
| 一个说明框，文件和采纳方案共同组成一次输入 | 保留自然语言操作，内部统一保存、解释、落实和追溯 | 采用 |

### 3.1 视觉和操作细节

- 上传前后均采用同一条 1040px 内容轴，小窗口两侧保留 24px；不因选中文件突然更换对齐或宽度。
- 标题、资料、说明、主操作顺序固定。移除大面积留白、大图标和独立的“下一步”宣传式卡片。
- 主 PRD 未选择时是一块紧凑的选择/拖入区域；选中后收为文件行。说明框从进入新建页就能输入，选文件不会清空文字。
- 说明框默认展开，约 6 行；长内容自然增高至约 12 行后滚动，提供“展开编辑”。它是表单，不做聊天消息气泡、问答向导或强制字段分类。
- 添加文件、目录贴近资料清单。默认用途为补充资料，单个文件可改为历史参考。目录名称沿用所选目录；更改路径放在目录项的可选设置里，避免当前常驻输入占据主流程。
- 大量附件显示总量和前几项，展开后可搜索、分页、修改用途或移除；首屏不重复展示主 PRD。完整路径在明细中可读，长文件名不挤压操作区。
- 本机保存状态与主按钮同一行；编辑中、保存中、已保存、保存失败用准确文案。已保存仅表示草稿持久化，未点击开始不运行。
- 原有重命名和删除能力保留在“继续上次准备”展开区域的所选草稿旁，脱离主要阅读轴；删除继续明确范围并确认。
- 主按钮为“开始分析”。文件清单、内容检索和读取记录归入下方按需展开区；“建立索引”不再是用户必须理解并手动执行的一步。
- 1280×800 下应同时看到主文件、说明输入和开始按钮。长内容时使用页面自然滚动，必要的底部操作条不遮挡输入焦点。

## 4. 首次分析流程

1. 用户选 PRD、按需加资料、输入说明。三者共同作为准备草稿保存。
2. 点击“开始分析”，主进程接收当前完整草稿，以一次提交冻结文件版本和全部文字。防重复提交标识随这一提交保存；失败重试不能重复创建任务。
3. 确认任务接收后进入任务详情。后台自动读取新增或变化文件、准备来源索引、理解本次说明、分析需求，统一显示阶段和真实进度。已经有效的解析结果直接复用。
4. 在功能识别前，提取说明中的全局范围、明确事实和整理要求，避免先按旧 PRD 完整分析一遍再修改。识别出功能后再绑定局部意见并提供相关原文。
5. 生成结果并核对产物依据。结果页提供“本次分析输入”，可看文件版本、用户原话、实际采纳方案，以及哪些意见已落实或待确认。

“一个开始动作”要由持久化的任务编排承接，不能只是页面等待索引结束后再调用创建任务；否则离开页面或重启会丢失后续动作。复用现有资料读取及调度器，补上同一次任务的准备阶段，不新建第二个独立执行系统。

文件不可读是输入处理错误，须具体说明文件及原因，可重试、替换或由用户明确排除非主文件。业务有歧义则生成对应待处理事项，继续生成已有依据的内容。两类状态不混用“需求阻塞”。不能把读取失败当成空文件继续。

## 5. 结果后的统一调整

沿用任务级“补充说明与调整”入口，用户仍只需要一次输入、一次提交：

- 可输入多条意见、添加补充文件，也可直接提交勾选的建议而不填文字。
- 选择或编辑建议后，在输入区上方显示“已选 8 项建议，其中 2 项已修改”，可展开查看、移除；不强制逐项确认。数量只统计本次选中项。
- 保存某条建议的修改仅保存草稿并加入本次选择；点击“按说明调整”才正式采纳。原推荐、用户修改稿、最终提交稿分别保留。
- 用户自由输入可以明确补充或替换某项建议。若自由输入本身存在无法确定的相反口径，仅把冲突点留下待确认，不按拼接顺序静默覆盖。
- 多项意见共同生成一个新版本；相关联的决定整体落实。独立意见可分别报告落实和待确认，无需因其中一句不明确让用户重填全部。
- 仅文字或建议变化时，沿用原文件索引，按相关功能落实；原始资料变化时复用文件解析，重新建立本次输入并执行资料变更所需分析。不承诺任意文档变动都能精准局部更新。

草稿属于一次准备或一次结果版本上的调整，不是资料文件的全局属性。恢复上次准备时恢复其文字和附件；选择复用已有资料新建任务时，不暗中继承历史任务说明。基于旧任务继续则继承已生效的业务结论和范围，并允许明确替换。

## 6. 一段文字如何处理

用户不用选择类型；平台内部区分含义，保留每条判断对应的原话。

| 用户输入示例 | 处理方式 | 作为业务事实？ |
| --- | --- | --- |
| “同名以去除首尾空格后完全一致为准” | 作为用户明确补充，关联需求及有关问题 | 是，来源显示用户补充 |
| “查询部分细化到字段和交互” | 调整已有依据的展开程度，缺少字段规则时不补造 | 否 |
| “自动合并本期不做” | 标记本期不做，保留原需求及来源 | 是范围决定，不是删除需求 |
| “历史原型只参考布局” | 限定该资料的用途和解释范围 | 是资料使用指令，不是功能规则 |
| “是不是应该自动合并？” | 保留询问语气；有依据可回答，无依据生成具体问题及建议 | 否 |
| “按建议方案 A 处理，但超时改成 15 分钟” | 采纳明确的修订结论，保留原方案及修改轨迹 | 提交后成为用户决定 |

事实和冲突规则：

1. 主 PRD 是基础。用户明确补充可新增事实；明确修改已有规则才替换相应口径，保留旧依据及替换关系。
2. 文件新旧或上传顺序不代表优先级。历史参考不自动覆盖主 PRD；补充文件出现冲突而用户未决定时，列出具体冲突。
3. 同次说明内有两个相反且无法消解的明确决定，不使用“最后一句获胜”。只就这一点给出待确认内容，说明当前依据、影响和建议。
4. 尚未采纳的生成建议不进入业务证据。用户修改建议后，原有推荐依据不自动变成修改稿的依据；界面区分“平台原建议”与“用户修改”，新结论引用用户提交原话。
5. 澄清关闭须以新结果已正确承接答案为准，不能在点击选择、保存修改或提交排队时关闭。
6. 待处理保留阻塞、建议、可忽略三级；不新增另一套“需求评审”待办。存在未决项仍可交付，并在交付内容中带上事项及影响。

## 7. 输入保存与来源结构

统一的提交记录至少包含：主资料版本、补充资料版本、完整说明原文、所基于的结果版本、采纳的建议及实际文本、提交时间和防重复标识。

实现上扩展现有类型和流程：

- 草稿与已提交快照分开。草稿保存使用版本校验；慢响应不能覆盖新输入，切换任务/版本不能串稿。点击开始时提交当前编辑值，不依赖某次自动保存恰好完成。
- 文件版本变化和说明变化分别管理。改文字不使文件索引失效，但必须改变任务输入版本；`sourceHash` 只覆盖文件不够表达本次完整输入，需记录整个提交的内容指纹。
- `UserEvidence` 复用用户来源能力，补齐首次分析时尚无功能编号的作用域表达；原话必须可回查，模型拆分摘要不能冒充原文。
- 采纳建议传结构化数据，包含事项标识、基础结果版本、原建议指纹、最终采纳文本；检查事项是否有效及原方案版本是否匹配。不能再用“反馈是否包含原推荐文字”证明采纳有效。
- 不通过模型从拼接字符串猜测哪些建议已被采纳。所选建议、自由说明、附件都完整持久化并传入实际处理流程；保留用户例外意见及其与所选方案的替换关系。
- 重试使用原提交快照；用户改变输入后属于新提交。运行中保存的新草稿不悄悄改变已执行节点，也不自动发起下一轮。
- 用户界面引用显示“主 PRD · 章节”“用户补充 · 本次分析”和相关原话，不暴露内部来源编号。交付产物保留有效决定、依据和未决项，不把未提交草稿当已确认结论。

## 8. 提示词与处理成本

统一输入不等于把所有材料和历次意见粘给每个 Agent。

- 本次意见仅解释一次，保留原话、意图及定位信息；首次定位分为功能识别前全局约束、功能识别后局部绑定。
- 节点只接收仍有效的全局约束、与当前功能有关的原文和用户结论。被明确替换的历史决定留在追溯记录，不重复注入为有效规则。
- 内容超过节点预算时按真实边界分组，不截断用户原话或静默丢弃后半段。记录实际 Token 和耗时作为后续优化依据。
- 核查重点是“生成主张是否有据、意见是否正确落实、关闭事项是否成立”。不增加全量语义查漏循环，也不把没有找到遗漏作为完整性证明。

## 9. 实施边界与顺序

1. 先统一草稿、输入快照、采纳建议的契约及存储，修正原文字串校验。
2. 首次分析在读取资料和功能识别前接入用户说明，打通一个开始动作及持久化准备状态。
3. 改准备页布局，结果页复用相同说明编辑及提交规则；保留批量选择、原地编辑和一次提交。
4. 补齐结果追溯、落实反馈、交付内容与说明文档；同步 `DESIGN.md`。
5. 用真实 Electron 实例验证完整输入链路和所有展开状态后再交付。

不更改需求完整性目标，不增加逐项强制审批，不建设聊天产品，不顺带重写任务中心或模型运行架构。

## 10. 验收计划及反证

以下是待执行用例，不是已通过结果。实施时按仓库规范建立用例矩阵和逐轮证据。

| 用例 | 必须看到的结果 |
| --- | --- |
| 只传定版 PRD、说明留空 | 一次开始即可完成，说明不成为必填项 |
| 先写说明再选/更换主 PRD | 草稿原样保留，提交使用屏幕上的最新文件和文字 |
| 一段含范围、事实、粒度、询问 | 四种意图正确区分；询问和粒度不被写成新业务规则 |
| 首次补充与 PRD 明确冲突且指定替换 | 第一次分析就采用明确决定，保留双向来源，不先生成旧结果再调整 |
| 同次说明两条规则互相矛盾 | 问题准确引用两处口径，其他独立意见仍可落实 |
| 批量采纳 20 项、手改 2 项、文本加 1 条例外 | 单次提交；最终文本一致，无原推荐字符串拒绝，例外正确作用 |
| 手改未提交或选中后取消选择 | 不生效，不关闭事项，不进入正式交付 |
| 输入 5000 字并附多个文件 | 无截断；保存、定位、提交和追溯都包含末尾内容 |
| 保存失败、快速连续输入、重启、重复点击 | 输入不丢、不串版本、不重复创建任务，状态文案准确 |
| 开始后离开准备页/重启 | 同一次任务按记录继续准备和分析，无需用户回到页面补点按钮 |
| 修改文字后再开始 | 文件解析结果复用，新的输入快照包含新文字 |
| 旧结果上编辑期间生成了新版 | 保留旧草稿，提示基准已更新；不能自动把旧选项提交到新版 |
| 建议已采纳但落实失败 | 保留具体未决事项，不因已点击采纳而假关闭 |
| 仍有待处理事项时交付 | 可交付，产物包含未决项及影响 |
| UI 明细 | 截图检查初始/已选/长文本/多文件/目录设置/方案编辑/选择摘要/失败反馈；检查键盘焦点与弹层遮挡 |

主要盲点：自然语言目标定位和冲突识别仍存在误判可能。实现前后都不能以结构校验或页面截图证明语义效果，需要固定混合意见样本及真实 PRD 运行结果反查。归纳不明的具体意见应原话呈现，不能要求用户把全部输入改填成结构化表单。
