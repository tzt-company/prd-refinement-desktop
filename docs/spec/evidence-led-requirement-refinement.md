# 有依据的需求整理与按需调整

2026-09-12，用户改变产品目标后的新方案。状态：待实施。本文件替代此前以穷尽遗漏、反复完整性审计为核心的后续规划；既有来源追溯、持久化和恢复能力继续复用。

## 产品目标

输入是已经定版、准备交给开发 Agent 的 PRD。平台提供一版有依据、可读、可调整的功能与需求整理结果。细化粒度由用户按实际开发需要判断，不建立“必须识别全部细节”的完成标准。首轮结果允许后续补充与重生成，但不能把原文未给出的业务规则伪装成确定需求。

不再采用“降低模型成本但保留原完整性循环”，因为目标未变；不只在原流程末尾增加编辑按钮，因为用户仍需等循环结束。采用一次有据生成、检查所产出的内容、按需局部调整。

## 依据契约

- 正式业务内容依据为冻结 PRD、用户提供的补充资料、用户明确提交的补充或澄清答案。后两类同样记录作者、时间、适用范围和版本，用户无需另写文档。
- 原文归纳、同义改写、联合多条明确规则推导允许；数字阈值、权限、状态变化、默认值、例外和验收要求必须有支持依据。仅挂来源编号而内容不受该原文支持，仍属于无依据内容。
- 功能名称、分组、句式、拆分粒度属于组织表达，不要求逐字来自原文。命名不得引入新的业务范围。
- “更细”“更简洁”等整理指令只控制表达，不作为业务事实。“超时按 30 分钟处理”等新规则属于用户补充，保存后成为新的明确依据。
- 用户补充与 PRD 冲突时，不按时间自动覆盖。只有用户明确说明替代哪条口径，才将新说明作为该范围的有效决定，否则保留具体冲突待澄清。
- 来源位置与版本可由程序校验；内容是否被来源支持仍需语义判断，不能将前者宣传为后者的百分之百证明。

## 首轮流程

资料读取 → 功能整理 → 按功能生成需求与澄清 → 依据核查 → 展示结果。

资料读取保留实际文件及原文索引；读取失败明确提示。功能整理保留首轮全文组织与明显重复处理，但不再以每段原文必须映射成需求为交付门槛。

依据核查从产物回看证据，检查引用有效、主张受到支持、是否曲解否定/条件、澄清是否把已知规则反问给用户。只检查产物忠实性，不展开全篇反向补漏，不以需求条数或颗粒度判失败。没有依据的业务内容修正、移出当前可用需求或标记待核查；不得自动改造成“PRD 缺失”的业务问题。

自动修正默认至多一轮，然后完成该功能或明确标记该功能核查失败；保留其他功能结果，不继续派生全面审计与无限返工。具体原文冲突属于业务澄清，不使“结果生成”失败。

## 三个调整入口

### 功能与需求：调整本功能

沿用现有功能页和需求详情，增加“调整细化”入口。提供“展开细化”“合并精简”和自由描述，用户可以指定条目或整个功能。

例：把“完成关联 ID 合并”展开为选择合并组、选择目标 ID、选择数据范围、确认后处理；只展开依据已说明的内容，不自动添加未规定的失败重试、权限或技术实现。若原文已经是最细信息，展示说明，用户可补充业务规则。

默认重新生成所选功能，输入包括该功能原文、已绑定公共约束、有效用户补充和本次指令；不重跑其他功能、全篇审计或整个任务。生成后展示新增、修改、删除及来源变化，默认展示新版本，可查看或恢复旧版本。

### 待澄清：填写答案并更新需求

每条显示问题、相关已知事实、具体未决点、影响、级别和原文。原文冲突需展示双方依据；“需要平台重新整理”“可能还有细节遗漏”不能成为业务澄清。

保留阻塞、建议、可忽略三级。阻塞仅表示相关范围无法确定实施行为，不表示整次整理失败。建议必须存在有依据的可实施口径；可忽略项不得改变业务行为。

支持“填写答案”“补充说明”“说明不适用”，可以合并多条答案后点击一次“更新相关需求”。答案先保存为用户补充，再生成受影响功能的新版本。只有新结果成功使用该答案、核查通过，才标记该澄清已处理。失败时保留答案和原结果，不要求重填。

### 任务：补充内容并重新生成

沿用资料准备页，支持添加说明、附件或替换 PRD。用户选择“更新指定功能”或“重新生成全部”；更换主 PRD 默认全量。公共规则变更展示来源关联到的功能，用户可以选择全部更新，不宣称自动影响分析覆盖所有语义联系。

输入以当前任务绑定的资料版本建立草稿，不隐式使用同名资料包最新版本。补充形成新输入版本，故障重试继续原版本；二者是不同入口。

## 版本与交付

同一任务有结果版本，记录基于哪版、调整内容、来源版本及更新功能。局部新版本替换目标功能，其他功能沿用上版；关系和澄清引用由程序校验，不允许悬空。历史答案、旧结果保留，失败不覆盖当前可用版本。生成以提交时的结果版本为基准；期间发生编辑时保留新候选并提示版本变化，不静默覆盖。

页面用“整理完成”“部分功能待核查”“有 N 项待澄清”表达事实，移除“已识别完整”“完整性通过”之类隐含穷尽承诺。原文覆盖率和平台审计条数不作为面向用户的质量分数。

允许导出当前结果及澄清清单；交给开发 Agent 时明确选定可实施范围。受阻或依据未核查的部分不混入可执行需求，放入单独待处理清单；无关功能不被连带阻断。JSON、Markdown、Excel 使用同一版本与范围。

## 实现落点与优先级

第一步更换生成完成条件：简化 scheduler 的完整性检查、反复补漏及跨节点返工，保留依据核查、证据协议、输入冻结、并发预算和检查点。保留已测的出处校验与联合证据能力，但只用于当前主张/具体澄清，不再全局穷尽扫描。

第二步在现有 App 功能/需求详情和 ResultIssues 抽屉接入局部调整、答案保存、局部重新生成和结果版本。复用 AnalysisTask 作为每次执行记录，用轻量任务与版本关联组织连续工作；不把所有历史输入灌进提示词。

第三步扩展 MaterialWorkspace 的补充草稿及同任务整轮重生成，再接入差异、历史版本与按范围交付。三个入口必须作为同一产品闭环交付，不仅更改页面文案。

## 验收场景

1. PRD 未说明超时阈值，结果不凭空出现“30 分钟”；来源编号存在但不支持该数字，同样不通过依据核查。
2. 两段原文共同支持一个结论，保留两段依据；不强求细化成固定数量的条目。
3. 同一功能可以展开或精简，业务含义和原文条件保持；其他功能不被重生成。
4. 用户回答一个澄清，答案有版本记录，新结果引用该答案，成功后原澄清不再重复出现。
5. 用户只说“再详细点”时，不能因此添加不存在的业务规则。
6. 补充或重生成失败，旧结果、已填写内容可恢复；改变主 PRD 后可追溯到新旧两个版本。
7. 一个功能仍有阻塞项，其他有依据的功能可单独交付，执行包不包含未获准实施的部分。

记录首轮出结果时间、局部调整耗时和提示词长度；20 分钟继续作为性能观察线，不恢复总时长终止，不设置无法定义的“细化完整率”指标。
