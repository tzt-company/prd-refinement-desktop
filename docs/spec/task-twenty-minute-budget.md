# 需求细化任务二十分钟执行方案

## 目标和范围

2026-09-11 用户明确：任务超过 20 分钟即视为流程有问题；2026-09-12 补充传给 Agent 的提示词长度也是优化重点。本方案补充 `task-execution-state-contract.md` 的执行预算，替换“逐问题串行确认和修复”的调度设计。既有 `runtime-performance.md` 主要处理上下文压缩和计时展示，无法承载本次执行路径和覆盖状态的变化，因此另存实施前快照。本轮只交付方案，不继续修改业务代码或新增验收任务。

目标是从点击开始分析到生成可查看交付结果不超过 20 分钟，包括任务排队、必要解析、模型等待、纠错、检查和导出。不能把工作挪到隐蔽的前置阶段或重置重试时钟来达标。已有资料准备时间另行展示，不能隐藏。以 15 分钟为优化目标，18 分钟为正常执行预算，保留 2 分钟处理延迟；这些是待实测的目标，不是当前能力结论。

20 分钟内必须完成平台整理，结果可为可交付或仅剩有依据的真实业务决定。到时强行停止且遗留平台问题属于性能验收失败，不能算成功。

## 路线选择

| 路线 | 结论 |
| --- | --- |
| 提高并发数字或全部换快速模型 | 不采用为主方案。串行代码不会因配置变快，低质量输出还会增加返工；当前细化已有快速模型增强纠错路径 |
| 删除复核或到 20 分钟直接标完成 | 不采用。减少校验不能证明交付正确，超时停止只算受控失败 |
| 减少重复工作、同上下文批量判断、无冲突范围并行、绑定总时限 | 采用。针对本次已经测得的主要耗时，并保留独立质量检查 |

## 新流程

冻结输入与预算 → 来源建账 → 功能识别与局部检查 → 一次全局统一 → 按功能并行细化 → 按完整业务上下文并行审计与批量确认 → 无冲突范围并行修正及复核 → 全局澄清与跨功能检查 → 同版本交付。

### 一、从源头关闭假工作

来源覆盖、语义确认、patch 准入共用同一份来源处置记录。每处原文必须有以下一种有证据的结论：已被某些需求承接、属于已有业务决定、背景或示例、存在真实未覆盖要求、证据不足。

- 已由其他段落对应的需求表达：绑定已有需求和相关字段证据，保存语义判定依据，不新增一条重复需求。
- 示例数值或背景：有依据地修正来源角色。例如原型 3、7、33 只有被原文规定为常量才生成固定值要求；不能仅凭数字或所在 DOM 自动排除。
- 确有独立遗漏：保留原来源和明确待补业务要求，进入修正。
- 尚不确定：保持内部未验证，不能将“审计不成立”解释为结构覆盖已完成。

这些状态和问题处置一次提交。最终结构检查读取同一记录；既不能用任意补引用骗过校验，也不能一边排除遗漏、一边继续因该遗漏重试。

### 二、一次读取同一上下文，批量确认

首轮审计保留独立于生成模型的职责。模型审计中已提供完整上下文、逐项证据和判断的观察，不再机械追加一遍单项确认。缺少上下文、脚本发现的未归属来源、同义观察和有争议事项集中到按功能及关联场景组织的确认批次；不同批次并行。每条输入必须显式返回 confirmed、already-satisfied、invalid 或 unknown，不能以空数组代表全部通过。

以本次 13 个功能为例，44 次小调用目标收敛为约 4–8 个上下文批次；分批按输入输出 token 预算确定，不为了凑次数截断材料。相互依赖的条件、表头、流程和验收条目进入同一包，跨包矛盾由全局检查覆盖。预计节省大部分 12.56 分钟串行等待，实际收益必须实测。

### 三、修正与复核真正并行

以写入范围合并相关问题；同一需求、功能归属或业务决定的修改合并成一个工作项。不同范围同时生成候选，候选完成即可独立复核，不等待其他范围全部完成；复核通过后经单写者队列依次短事务提交。模型调用不持有提交锁。

并行冲突不仅看写集合，还检查另一候选的读取实体和查询成员集合。确认遗漏依赖的整个检索范围必须登记；相关提交导致旧结论失效时只补受影响的检查，无关功能的改变不触发整批重跑。

单任务节点并发默认 10、最大并行任务默认 5。共享服务按真实可用额度限流并公平分配，不把配置乘积 50 当作上游保证；读取、生成和提交分别记录排队时间。5 个任务同时执行必须单独验收，不得只报告空载单任务成绩。

### 四、降低前半段返工与输出成本

候选以章节和完整业务场景为边界，相邻短段合包，共享上下文只发送一次；原文登记仍逐项保留。局部检查负责解决分类问题后再进入统一。统一中若发现边界争议，针对争议映射处理，其余已经通过的功能映射冻结；避免每次重发全量候选。影响全局范围的变化仍须补全局检查。

细化和修正只输出必要业务字段及证据选择，程序生成 ID、版本、默认状态等元数据。修正采用有类型的字段增量，未修改字段由程序保留；字段值和证据一起变更，不能用自由 JSON patch 绕过领域校验。普通功能是否使用快速模型由固定样本的一次通过率和“首次耗时＋返工耗时”比较决定；本次已发生重复失败的复杂证据输出直接分配能通过契约的现有模型档位，不能总是先花两次失败再升级。

对终态项目按现有代码只读重建澄清输入，不作为原请求逐字记录：原文正文共 34,039 字符；证据目录文本 63,925 字符、771 项；完整序列化节点输入 345,675 字符。其中 sourceUnits 114,982，evidenceCatalog 170,099，requirements 49,228，sourceContexts 9,480，clarifications 1,799 字符。依据是 `source-evidence.ts` 的整段加分句目录和 `scheduler-v2.ts` 的全部 sourceUnits、requirements 输入。

改造统一的节点输入构造器，先确定必须读取的材料，再序列化、计量和校验预算，最后才发请求：

1. **原文仅出现一次。** 请求保存按原顺序的非重叠证据片段及必要章节、表头、列表引导语；整段选择用片段组表示，完整父段不再次携带同一文本。程序维护原有快照和字符区间，模型仍只选证据 ID。反向展开必须无损保留顺序、空白和选区，多来源组合不能失真。
2. **长编号使用请求内短别名。** S1、E1、R1 等在单次请求内映射到持久 ID；映射表由程序绑定该请求和快照并持久化。模型只见短别名，输出解码时拒绝未知或其他请求的别名。持久证据 ID 和任务身份不变，避免把很长的文件 UUID 与修订号重复上百次。
3. **只发送节点需要的字段。** 来源索引读取解析后的正文、业务位置和必要上下文；省略磁盘路径、哈希、导入时间、重复标题和调度状态。修正工作项读取写入对象及确有依赖的只读对象；全局检查先覆盖所有决定和相关需求的轻量目录，再对每个决定补完整证据。不能以 Top-K 截断代替全量检查，也不能随意省略可能回答问题的流程、AC 或原型上下文。
4. **协议说明只出现一次。** 共用业务约束、当前节点职责和最小输出 schema 分开组织，去除嵌套 schema 中反复展开的三级澄清说明和重复示例。复核前后只发送 changedFields、原值与新值，再加一份必要只读上下文；反馈只保留当前未解决错误与有关字段，不叠加历次整段响应。
5. **按 Token 打包。** 批量确认共享一份上下文，问题列表受同一输入预算限制；达到预算则按完整场景拆批，不能机械合成巨型请求。必需上下文仍过长时按章节处理并安排跨章节一致性检查；无法满足预算要在发调用前明确报告，禁止静默截断或默认通过。
6. **同时约束输出。** ID、版本和状态由程序填充；既有条目只返回允许修改的字段及对应证据。控制要求的条目数与输出预算，避免输入变短却因大量解释和重复对象延长生成或触发截断重试。

初始应用侧完整文本输入预算如下，包含节点说明、schema、原文、业务对象和本次反馈；不包含 CLI 自带的隐藏系统开销。数值是待固定样本校准的设计起点，不能当作已实测限制：

| 请求 | 目标输入 | 拆包阈值 |
| --- | ---: | ---: |
| 候选识别、局部检查、普通细化 | ≤6,000 Token | 12,000 Token |
| 统一、批量确认、审计 | ≤10,000 Token | 16,000 Token |
| 复杂修正、独立复核、澄清判定 | ≤12,000 Token | 20,000 Token |

预检使用已知模型的可用 tokenizer；没有匹配 tokenizer 时用标明为估计的保守结果，不能用字符数除以四冒充精确计数。加上适配器开销估计、输出预留和安全余量后，还要满足已核验的模型上下文限制。记录应用提示长度与 provider 实际输入之间的差值；出现异常膨胀再检查适配器注入，不能只缩短业务正文。

每个逻辑节点及每次实际尝试记录：应用字符数/UTF-8 字节数、Token 估计及其算法、指令/原文/业务数据/schema/反馈占比、证据集合和请求哈希、实际输入/缓存/输出 Token、排队及执行时间。诊断只记录统计和必要本地依据，不默认打印完整 PRD。

验收同时满足 20 分钟与语义质量不下降；在同输入同适配器下，累计实际输入相对本次 806 万至少降低 60% 作为初始优化目标，应用提示 P95≤12,000 Token、无未经拆包处置的阈值超限。实际 Token 和字符各自统计，不能把费用下降、缓存命中或调用减少直接当作耗时达标。

### 六、固定截止时间和收敛规则

| 工作 | 计划时间 | 累计目标 |
| --- | ---: | ---: |
| 必要解析、来源建账与容量检查 | 1 分钟 | 1 分钟 |
| 功能候选、局部检查、统一 | 3 分钟 | 4 分钟 |
| 并行细化 | 4 分钟 | 8 分钟 |
| 审计及争议批量确认 | 3 分钟 | 11 分钟 |
| 并行修正及独立复核 | 5 分钟 | 16 分钟 |
| 全局澄清、跨功能检查与导出 | 2 分钟 | 18 分钟 |
| 延迟余量 | 2 分钟 | 20 分钟 |

预算是该真实样本的工程目标，允许阶段间借用空余，总截止时间固定。创建任务就保存 submittedAt 和 deadlineAt，恢复、换组、模型升级均不能重置。每次调用有独立超时，初始按普通调用 90 秒、复杂调用 120 秒试验，再按样本校准；实际调用上限取节点预算、剩余总时间和最终检查预留时间的最小值。当前 Runtime 默认单调用可等 10 分钟，必须受任务剩余预算约束。

修正保留首轮加一次有明确差异反馈的定点再修作为初始策略，计入同一总预算；相同输入、候选和失败原因不得盲目重复。已有候选或复核直接恢复；新发现问题归入剩余预算，不开启新的无限三轮。20 分钟到期停止派发并取消未完成调用，拒绝迟到提交，保留最后一致草稿并标记“平台处理超时”；超时不能当成业务阻塞，也不能经点击重试获得新的合格计时。

准入预计无法满足时尽早显示容量不足和原因，避免接下任务后无限排队；拒绝或超时仍计入失败率，不能用它们制造“所有完成任务都很快”的假成绩。扫描件或更大材料不能悄悄放宽时间，需另行验证容量。

## 实施顺序与验收

1. 固化当前调用时间线与覆盖状态矛盾反例，先修统一来源处置和真正的工作项恢复；补齐原子提交及读写依赖测试。
2. 实现统一节点输入构造器与长度计量，先消除证据文本、长编号和对象重复，建立 Token 预算；再按该预算引入上下文批次确认和无冲突并行修正，提交短事务串行。
3. 减少全局统一重跑与完整对象复写，接入端到端 deadline 和逐调用取消；输出契约失败反馈必须计入提示词长度和总调用预算。
4. 检查证明由实际完成的检查产生并绑定依赖及结果版本，最终只验证证明；禁止临到交付按 open=0 生成一套 passed。
5. 冻结代码、材料、模型和预算后执行至少三次新任务，另执行 5 个任务同时运行用例。每个任务都必须在 20 分钟内正常到达可交付或只有真实业务决定；不得人工改代码、补任务 JSON、延时或续跑。

性能与质量分别验收：记录从提交到导出的墙钟、调用排队/执行/提交时间、最长依赖链、首次契约通过率、重复请求数、拒绝与超时率。单样本三次通过只证明回归用例，不宣称生产 P95；P95≤15 分钟需更大样本集证据。
